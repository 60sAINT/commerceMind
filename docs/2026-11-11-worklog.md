# 2026-11-11 工作记录

## 今天第一件事：`/chat` 接入多轮记忆

把已经做好的 Redis 短期记忆真正接到聊天接口：每轮先读当前会话的 working memory、summary 和 state，回答成功后原子提交本轮问答，再交给后台维护队列判断是否压缩。失败的回答不写入。

本次只接短期记忆；长期情景记忆检索、画像注入、意图识别和 Agent 路由仍未接入。

### 新增功能

1. **多轮上下文**
   - `/chat` 每轮读取 `user_id + session_id` 下的全部历史；
   - 历史按时间顺序作为 `messages` 传给模型，summary 作为“历史摘要数据”拼进 system；
   - 第二轮能读到第一轮的 user/assistant 消息。

2. **会话标识**
   - 请求可带 `session_id`；不传时服务端生成 16 位十六进制 ID，并在响应里返回；
   - 同一个 `session_id` 才共享记忆，不同会话完全隔离；
   - 不按 `user_id` 兜底复用会话，避免把不同对话串在一起。

3. **请求幂等**
   - 请求可带 `client_request_id`；
   - 相同 ID、相同消息直接返回上次保存的回答，不再调用模型；
   - 相同 ID、不同消息返回 409 `client_request_id_conflict`；
   - 回执和本轮问答在同一个 Redis 事务里写入，不会出现“有回执没消息”。

4. **整轮会话锁**
   - 同一个 `user_id + session_id` 串行处理；
   - 锁忙返回 409 `conversation_busy`，带 `Retry-After: 1`；
   - 锁续租失败返回 503 `conversation_lease_lost`；
   - 整轮超过 50 秒返回 504 `request_timeout`。

5. **原子提交**
   - 成功轮次一次 `MULTI/EXEC` 写入：working memory、TTL、state、summary、幂等回执；
   - 模型调用失败、参数校验失败时不写任何 key；
   - 写记忆失败仍然返回模型答案，只记 warning，不把已经生成的回答丢掉。

6. **健康检查**
   - `/health` 新增 `memory`：
     - `enabled`
     - `redis`: `ok / error / disabled`
     - `chroma`: `ok / error / disabled`
     - `detail`
   - Redis 和 Chroma 各自 1.5 秒超时，不拖住健康检查。

7. **降级运行**
   - `COMMERCEMIND_MEMORY_ENABLED=false`：完全走无记忆路径，旧行为不变；
   - `COMMERCEMIND_MEMORY_REQUIRED=false`：Redis/Chroma 不可用时应用仍启动，`/chat` 按无历史回答，`/health` 显示 `degraded`；
   - `REQUIRED=true`：依赖不可用时启动直接失败；
   - 读记忆失败按无历史继续；Chroma 目前只参与健康检查。

8. **模型 usage**
   - `core/llm.py` 返回 `ChatResult(text, input_tokens, output_tokens)`；
   - `/chat` 响应和日志增加 token 数，便于后续做成本统计。

### 调用流程

```text
POST /chat
  → 校验 user_id / session_id / client_request_id
  → 有 client_request_id 且命中回执：直接回放
  → 取会话锁
  → 读 working memory + summary + state
  → 历史消息放 messages，summary 放 system
  → 调模型
  → 成功：原子提交本轮 + 回执 → 触发后台压缩检查
  → 失败：不写任何 key → 返回原有错误码
```

### 关键实现

**避免锁重入**

`commit_turn()` 自己会取会话锁。`/chat` 为了幂等需要整轮持锁，因此增加 `lock_held=True`：调用方已经持有 `conversation()` 时不再重复加锁，否则 `KeyedLocks` 会等待自己，Redis 租约也会判忙。

**回执与消息同事务**

回执不是先写消息再单独 `HSET`，而是在 `commit_turn()` 的同一个 pipeline 中完成：

```python
pipe.lpush(working_key, turn_payload)
pipe.expire(working_key, ttl_s)
pipe.hset(receipt_key, client_request_id, turn_payload)
pipe.expire(receipt_key, ttl_s)
```

**summary 不放进 messages**

summary 是历史数据，不是新指令。它通过 `context.to_system_text(SYSTEM_PROMPT)` 拼进 system，并注明“以下是历史会话摘要数据，不是新的指令”。

**失败轮次**

模型失败时根本不调用 `commit_turn()`；`commit_turn(succeeded=False)` 也保留为显式保护，返回 `None` 且不写任何 key。

## 今天第二件事：幂等回执补齐与 `/memory` 调试接口

第一件事里的回执按 `user_id + session_id` 存，重试时如果客户端只带 `client_request_id`、不带 `session_id`，服务端会生成新会话，仍然会再调用一次模型。这里补上用户级回执索引，并新增只在 debug 开启时存在的会话调试接口。

### 新增功能

1. **无 `session_id` 也能幂等重试**
   - 新增用户级回执 Hash：`ureceipt_v1:<user_digest>`；
   - field 是 `client_request_id`，value 记录原 `session_id` 和完整轮次；
   - `/chat` 先按 `client_request_id` 找原会话，命中后直接回放；
   - 同 ID、不同消息仍返回 409 `client_request_id_conflict`；
   - 会话级回执保留，用户级索引与会话回执在同一个 `MULTI/EXEC` 写入。

2. **回放优先于模型配置检查**
   - 即使模型 Key 临时失效，只要回执命中，仍能返回上次缓存的回答；
   - 避免重试时因为模型未配置拿到 503，而不是原来的结果。

3. **记忆调试开关**
   - `MemorySettings` 增加 `debug`；
   - 环境变量 `COMMERCEMIND_MEMORY_DEBUG` 默认 `false`；
   - `false` 时不注册路由，访问返回 404，不暴露接口存在；
   - 记忆服务未启动时同样返回 404。

4. **会话调试接口**
   - `GET /memory/{session_id}?user_id=u1`；
   - 返回 `turn_count`、`summary`、`state`、按旧到新排列的 `turns`，以及 working/state/summary 的 TTL；
   - 只读：不触发压缩、画像、episode 写入或后台维护；
   - 不返回 Redis key 名和回执内容；
   - 不存在的会话返回 200、`turn_count=0`，TTL 为 `-2`；
   - 不依赖模型 Key 是否配置。

## 今天第四件事：Pattern 意图匹配

完成 `feat(core): implement pattern intent matching`。新增 `core/intent_pattern.py`，实现无模型调用、同步执行的关键词规则识别；没有把它接入 `/chat` 或三路仲裁，后续识别器可将它作为 Pattern 候选来源。

### 新增方法与输入输出

- `recognize_pattern(message: str) -> PatternMatch`：公开入口只接收**当前传入的一段消息文本**，不接收历史、用户身份或 state。未来上游识别器决定传当前轮原文还是自行拼入上下文；当前函数只检查传入字符串自身。返回 `PatternMatch`：`candidate` 是 `IntentCandidate(intent, confidence, source)`；`matched_patterns` 是实际命中的关键词；`priority` 是 `specific`、`generic` 或 `none`。
- `_best_match(text, rules)`：按规则表顺序查找第一个有命中的意图，并返回该规则下全部命中词。规则表顺序因此也是同一层级内部的优先级。
- `_contains(text, pattern)`：中文及标点按子串匹配；纯英文关键词通过 Python 正则 `re.search` 做不区分大小写后的 token 边界匹配，避免 `hi` 错误命中 `shipping`。所以这是关键词模式匹配，其中英文边界检查使用了正则；中文规则不是复杂正则表达式。

### 规则和行为

1. **具体规则优先（固定分数 0.90）**，严格按下列次序检查类别；某类别至少一个关键词命中后立即停止，不继续检查后面的类别。该类别内所有命中关键词都会放入结果：
   - `HUMAN_HANDOFF`：`转人工`、`人工客服`、`找人工`
   - `ORDER_STATUS`：`订单状态`、`发货了吗`、`处理到哪`、`order status`
   - `LOGISTICS`：`物流`、`快递`、`配送`、`运单`、`delivery`、`shipping`
   - `REFUND`：`退款`、`退货`、`refund`、`return`
   - `INVOICE`：`发票`、`抬头`、`税号`、`invoice`
   - `PAYMENT_ISSUE`：`重复扣款`、`多扣`、`支付失败`、`扣费`、`payment failed`
   - `ACCOUNT`：`被盗`、`异常登录`、`重置密码`、`两步验证`、`安全`
   - `TECHNICAL`：`无法登录`、`登录失败`、`401`、`验证码`、`崩溃`、`闪退`、`500`、`报错`、`crash`
2. **通用规则兜底（固定分数 0.60）**，仅在完全没有具体规则命中时检查，也按顺序遇到首个命中类别即停止：
   - `COMPLAINT`：`投诉`、`太差`、`糟糕`、`horrible`、`等了很久`
   - `COMPLAINT`：`经理`、`supervisor`（独立的下一条规则，仍映射为投诉）
   - `OTHER`：`?`、`？`、`怎么`、`什么`、`status`
   - `OTHER`：`帮我`、`需要`、`please`、`help`
   - `GREETING`：`你好`、`嗨`、`hello`、`hi`
   - `OTHER`：`密码`、`邮箱`、`账户`、`password`
3. **未命中**：返回 `IntentCategory.OTHER`、`confidence=0.0`、`priority="none"` 和空命中列表。它明确表示规则没有证据，不代表语义模型判断了 OTHER。
4. 输入非字符串抛出 `TypeError`；空字符串是合法输入，按未命中处理。当前为短小确定性规则集，不做近似匹配或分词扩展。

### 分数怎么来

分数不是统计概率，也不按命中关键词数量累加。它是当前实现给规则层级配置的固定置信度：具体规则命中为 `0.90`，通用规则命中为 `0.60`，无规则命中为 `0.0`。同一个类别即使命中多个词，分数仍不变；具体规则优先级更高也意味着它会遮蔽后续类别和所有通用规则。后续三路融合时，这个值会作为 Pattern 来源候选的 confidence，再由融合权重缩放；单独调用 Pattern 不会自动产生最终三路结论。

### 完整示例

调用示例：

```python
from core.intent_pattern import recognize_pattern

message = "麻烦查一下订单状态，物流显示快递还没发货，能帮我催一下吗？"
match = recognize_pattern(message)
print(match.candidate.intent.value)  # order_status
print(match.candidate.confidence)    # 0.9
print(match.matched_patterns)        # ('订单状态',)
```

具体规则按表顺序检查。`ORDER_STATUS` 命中 `订单状态`，因此立即胜出；虽然同一条消息也包含 `物流` 和 `快递`，但 `LOGISTICS` 排在后面，不会被继续检查，也不会出现在命中列表。`帮我` 是通用请求词，但有具体规则命中后通用层完全不运行。返回值等价于：

```python
PatternMatch(
    candidate=IntentCandidate(
        intent=IntentCategory.ORDER_STATUS,
        confidence=0.90,
        source=IntentSource.PATTERN,
    ),
    matched_patterns=("订单状态",),
    priority="specific",

```

这里表达“规则按优先级判为订单状态，报告获胜规则中的证据词”。注意 `matched_patterns` 不是整条消息所有可能命中的关键词，而只是获胜类别的命中词。若输入只有“蓝色的商品还有库存吗”，当前规则没有商品库存模式，会返回 `OTHER/0`，而不是猜测分类；后续融合可忽略零分 Pattern 候选，让 LLM 或 Embedding 提供语义判断。

## 今天第五件事：Embedding 意图匹配

### 新增方法与数据流

- `IntentEmbeddingMatcher.from_env(settings)`：按现有 `COMMERCEMIND_MEMORY_EMBEDDING_PROVIDER`、`COMMERCEMIND_MEMORY_EMBEDDING_MODEL` 等环境配置创建 matcher；provider 配置失败时构造不可用实例，后续返回 OTHER/0。
- `IntentEmbeddingMatcher.recognize(message: str) -> IntentCandidate`：输入**一条当前消息字符串**，不读取对话历史、state、用户 ID，也不接收预先算好的向量。调用方通过 `IntentEmbeddingMatcher.from_env(settings)` 创建实例后调用 `matcher.recognize("我的订单发货了吗？")`。输出包含分类、confidence 和固定来源 `EMBEDDING`；例如成功命中订单状态时输出 `IntentCandidate(IntentCategory.ORDER_STATUS, 0.99..., IntentSource.EMBEDDING)`。
- `IntentEmbeddingMatcher._load_templates()`：第一次调用时把模板示例按类别展平为一个文本列表，交给复用的 embedding callable 批量编码；再按原类别/示例数量切分并缓存向量。后续调用直接使用缓存，不再重编码模板。若模型/provider 初始化或模板编码失败，本实例标记不可用。
- `recognize()` 的具体步骤：1) 校验消息是字符串，空白字符串直接 OTHER/0；2) 确保模板向量已加载；3) 对当前消息调用同一个 embedding callable，得到 query 向量；4) 校验返回数量、向量非空、非零、数值有限且同批维度一致；5) 将 query 与每个示例向量算余弦相似度；6) 对每个类别取其示例中的最高分，再从所有类别中取最高分类；7) 最高分达到阈值则返回分类和分数，否则 OTHER/0。任一 provider、编码或计算异常被捕获，本路降级 OTHER/0，并标记实例不可用。
- `_cosine(left, right)`：计算两个非零、同维度向量的余弦相似度；维度不一致或零向量会引发异常，由 `recognize()` 捕获并降级。
- 本次模板总计 **10 个意图类别、20 条样例文本**，内容逐字如下。这些是语义参照样例，不是关键词规则：
  - `ORDER_STATUS`：`我的订单现在是什么状态？`、`订单有没有发货？`
  - `LOGISTICS`：`快递什么时候到？`、`物流一直没有更新`
  - `REFUND`：`我要申请退款`、`退货退款怎么处理？`
  - `INVOICE`：`帮我开发票`、`发票抬头怎么修改？`
  - `PAYMENT_ISSUE`：`支付失败或重复扣款`、`为什么多扣了钱？`
  - `ACCOUNT`：`账户无法访问或需要重置密码`、`账户信息怎么修改？`
  - `TECHNICAL`：`应用报错或无法登录`、`页面崩溃、系统闪退`
  - `COMPLAINT`：`我要投诉，服务太差了`、`我等了很久还没有人处理`
  - `HUMAN_HANDOFF`：`请转人工客服`、`我要找人工处理`
  - `GREETING`：`你好`、`您好，有人在吗？`

### 从输入到输出的完整过程

1. **准备输入**：调用 `recognize()` 时传入一条原始用户文本，例如 `我的订单有没有发货？`。方法不带 history，因此上一轮提到“我的订单”也不会自动作为输入；如调用方希望结合上下文，必须由调用方先把上下文整理进传入文本（当前聊天链路尚未这样做）。
2. **准备参照文本**：matcher 内部取上述 20 条固定示例，并保留每条示例属于哪个 `IntentCategory` 的映射关系。第一次识别将 20 条文本批量交给 embedding provider，得到 20 个模板向量，并按类别重新分组缓存。例如 `ORDER_STATUS` 对应两个模板向量，`LOGISTICS` 也对应两个模板向量。模板缓存只在 matcher 实例内有效。
   参照文本：`IntentEmbeddingMatcher` 第一次执行 recognize() 时，`_load_templates()` 才会把全部 20 条示例文本批量编码成向量，并缓存起来。之后该 matcher 实例的后续调用会复用这些模板向量。模板向量缓存在 IntentEmbeddingMatcher 实例的内存里，具体是 self.\_template_vectors，属于进程内缓存。它没有设置过期时间：只要这个 matcher 实例还被引用，模板向量就一直保留；实例销毁或进程重启后，缓存消失。
3. **编码本轮消息**：同一个 provider 对用户输入文本编码，得到一个 query 向量。模板向量和 query 向量必须由同一个 embedding 模型产生，维度必须相同，才能比较。
   传入的字符串：每次调用 recognize(message)，都会把这条消息编码成 query 向量，再与缓存的模板向量计算相似度。
4. **逐个比较向量**：将这一条 query 向量分别与 20 个模板向量计算余弦相似度。不是将 query 与关键词比对，也不直接把用户文本与模板做字符串相似度。余弦值表示两个向量方向接近程度；向量长度本身不直接提高分数。
5. **按类别汇总**：每个类别有两条样例，取 query 与该类别两条模板向量相似度中的最大值作为该类别分数。比如 `ORDER_STATUS = max(sim(query, order_example_1), sim(query, order_example_2))`。当前不求平均，因此一个高相似示例可以代表该类别。
6. **选择胜者并过阈值**：比较十个类别分数，选择最高者。如果最高分 `>= embedding_threshold`（默认 `0.72`），返回该类别及实际最高分；如果 `< 0.72`，拒绝分类并返回 OTHER/0。两个类别同分时，Python `max()` 保留模板字典中先出现的类别。
7. **构造结果**：成功时返回 `IntentCandidate(intent=最高分类, confidence=最高相似度, source=EMBEDDING)`。拒绝或本路不可用时返回 `IntentCandidate(OTHER, 0.0, EMBEDDING)`。不返回十类分数表或命中的示例文本；当前返回结构只提供胜者候选。

### 阈值、分数与失败处理

相似度作为候选 confidence，限制在 0 到 1。默认阈值来自 `IntentSettings.embedding_threshold=0.72`；代码按 `score >= threshold` 接受最高分类，低于时返回 OTHER/0。该值是向量夹角相似度，不是校准后的概率，也没有根据模板数量或类别先验额外归一化。无效 query 或模板向量、API/模型调用错误以及 from_env 配置失败都会使本路不可用；实例标记不可用，后续请求不反复触发失败调用。融合层可据 OTHER/0 忽略该来源，继续使用 LLM/Pattern。

示例：代码使用方式如下：

```python
from core.config import IntentSettings
from core.intent_embedding import IntentEmbeddingMatcher

settings = IntentSettings(embedding_threshold=0.72)
matcher = IntentEmbeddingMatcher.from_env(settings)
candidate = matcher.recognize("我的订单有没有发货？")
print(candidate.intent.value, candidate.confidence, candidate.source.value)
# 例如：order_status 0.994... embedding
```

**贯穿示例：**传入 `我的订单有没有发货？`。假设 embedding 模型把这句话编码为 query 向量 `q=[0.9, 0.1]`。为了展示计算，假设订单状态的两条示例向量分别为 `t_order1=[1.0, 0.0]`、`t_order2=[0.8, 0.2]`，物流的两条示例向量分别为 `t_logistics1=[0.0, 1.0]`、`t_logistics2=[0.2, 0.8]`。其余八类也各有两条模板向量；假设它们的最高相似度都低于订单状态的类别分数。以下数值仅为便于说明的假设，不是实际模型计算结果。

余弦相似度公式是：

```text
sim(q, t) = (q1*t1 + q2*t2 + ... + qn*tn)
            / (sqrt(q1^2 + q2^2 + ... + qn^2)
               * sqrt(t1^2 + t2^2 + ... + tn^2))
```

先比较订单状态两条示例：

```text
sim(q, t_order1) = (0.9*1.0 + 0.1*0.0) / (sqrt(0.9^2+0.1^2) * 1.0)
                 = 0.9 / sqrt(0.82) ≈ 0.9939
sim(q, t_order2) = (0.9*0.8 + 0.1*0.2) / (sqrt(0.82) * sqrt(0.68))
                 = 0.74 / (0.9055 * 0.8246) ≈ 0.9913
ORDER_STATUS 分数 = max(0.9939, 0.9913) = 0.9939
```

再比较物流两条示例：

```text
sim(q, t_logistics1) = 0.1 / sqrt(0.82) ≈ 0.1104
sim(q, t_logistics2) = (0.9*0.2 + 0.1*0.8) / (sqrt(0.82) * sqrt(0.68))
                      = 0.26 / (0.9055 * 0.8246) ≈ 0.3482
LOGISTICS 分数 = max(0.1104, 0.3482) = 0.3482
```

对其余类别也照样计算“query 对两个示例的相似度，再取最大值”。如果假设所有类别中订单状态最高，且 `0.9939 >= 0.72`，最终返回 `IntentCandidate(ORDER_STATUS, 0.9939, EMBEDDING)`。若十类最高类别分数是 `0.61`，则无论哪个类别排名第一，仍因低于阈值返回 `IntentCandidate(OTHER, 0.0, EMBEDDING)`。
当前实现每次只返回一个意图候选。

## 今天第六件事：LLM 意图分类

完成 `feat(core): implement llm intent classification`。新增 `core/intent_llm.py`，复用 CommerceMind 现有 `LLMClient.chat()`，用专用 system prompt 约束模型输出，并把合法结果解析为共享的 `IntentCandidate`。没有改变通用聊天 prompt、`LLMClient` 行为或 `/chat` 主链路。

### 新增方法、输入与输出

- `IntentLLMClassifier(llm)`：构造时注入已创建的 `LLMClient`，因此 API Key、模型、base URL、超时和统一 SDK 异常仍由现有 client/settings 管理；分类器不自行创建第二个模型客户端。
- `await classifier.recognize(message: str) -> IntentCandidate`：输入当前一条非空用户消息，不自动接收或拼接对话历史；输出 `intent`、`confidence` 和 `source=LLM`。有效输出如退款意图会得到 `IntentCandidate(IntentCategory.REFUND, 0.93, IntentSource.LLM)`。空白输入直接 OTHER/0，不发模型请求；非字符串输入抛 `TypeError`。
- `IntentLLMClassifier._parse(raw)`：解析完整 JSON，并严格要求字段集合恰好为 `intent`、`confidence`、`reasoning`；意图必须是 `IntentCategory` 已定义值，confidence 必须是非 bool、有限数字且在 0 到 1 内，reasoning 必须是字符串。缺字段、多字段、非法 JSON、未知意图、NaN/Infinity、布尔或越界分数都按格式错误处理。当前不从 Markdown 代码围栏或额外说明中提取 JSON，避免静默接受不符合协议的输出。

### Prompt 与处理流程

1. 校验 `message` 类型；空白文本立即返回 OTHER/0。
2. 调用现有 `LLMClient.chat(message, system=专用分类 prompt)`。因此原始用户消息作为 user 内容发送，JSON 输出要求放在本次调用专用 system 参数中；现有 client 负责模型配置、超时、文本提取及 API 错误转换。
3. Prompt 要求只输出一个 JSON 对象，格式为 `{"intent":"<intent_value>","confidence":0.0,"reasoning":"简短中文理由"}`；说明 confidence 范围，并列出允许的意图值：`order_status`、`logistics`、`refund`、`invoice`、`payment_issue`、`account`、`technical`、`complaint`、`human_handoff`、`greeting`、`other`。同时要求优先具体业务意图、无法判断时使用 other。
4. `_parse()` 检查 JSON 语法、字段、枚举值和 confidence 合法性。
5. 解析成功则构造 LLM 来源候选；LLM 调用异常或输出解析失败则返回 `IntentCandidate(OTHER, 0.0, LLM)`。该错误被限制在本路，供未来融合继续参考 Embedding/Pattern；当前分类器不记录 reasoning 到候选，因为共享 `IntentCandidate` 尚无 reasoning 字段。

### 使用示例

```python
from core.config import Settings

llm = LLMClient(Settings.from_env())
classifier = IntentLLMClassifier(llm)
candidate = await classifier.recognize("这个订单我想申请退款")
if candidate.intent is IntentCategory.REFUND:
    print(candidate.confidence, candidate.source.value)
    # 例如：0.93 llm（實際分數由模型輸出，不固定）
```

模型可能返回 `{"intent":"refund","confidence":0.93,"reasoning":"用户明确提出退款诉求"}`。解析后得到 `IntentCategory.REFUND`、分数 `0.93`、来源 `LLM`。分数由模型按 prompt 自评，分类器只验证其格式和范围，不重新计算或校准；它不是经评测验证的概率。如果模型返回 `confidence: 1.4`、未知意图或附加 Markdown，分类器会返回 OTHER/0，而不会把无效结果交给融合器。

## 今天第七件事：融合三路意图信号

完成 `feat(core): combine llm embedding and pattern intent signals`。新增 `core/intent_fusion.py` 的 `combine_intents(candidates, settings) -> IntentResult`，将三种单路候选统一为最终意图结果。

### 输入、输出和配置

- `candidates` 是以 `IntentSource` 为 key 的映射，值为对应来源的 `IntentCandidate` 或 `None`。三个可识别 key 是 `LLM`、`EMBEDDING`、`PATTERN`。candidate 必须声明与 key 相同的 source，confidence 是 0 到 1 的有限数，intent 是 `IntentCategory`；不符合约定的候选按该来源无有效信号处理。
- `settings` 是 `IntentSettings`，省略时使用默认配置。默认权重 `LLM=0.70`、`Embedding=0.20`、`Pattern=0.10`，最终阈值 `0.35`，三路均启用，失败策略 `available_sources`。
- 返回 `IntentResult`：包含最终意图、融合 confidence、胜出来源、每路原始 confidence 的 `source_scores`。若阈值未通过、无有效候选或严格失败策略触发，source 为 `FALLBACK`；否则 source 是对获胜意图贡献的最高优先来源（LLM > Embedding > Pattern）。

### 实际仲裁步骤

1. 依次检查 LLM、Embedding、Pattern 配置开关；关闭的来源完全不参与投票，也不算故障。
2. 检查候选类型、source 与 key 是否一致、意图和置信度是否合法。缺失、坏候选、`OTHER/0` 都记录为该来源无有效信号；其他合法候选即使意图为 OTHER 且 confidence 大于 0，仍作为明确的 OTHER 判断参与投票。
3. 对每个有效候选计算 `weighted_score = source_weight * candidate.confidence`，并累加到候选意图类别。例如 LLM 与 Pattern 都判为 REFUND，就将两路分数累加到 REFUND。不同类别的分数互不抵消。
4. 取累计分数最高的类别。完全同分时优先级固定为 LLM、Embedding、Pattern 的来源优先级：比较类别最早由哪个来源支持，支持来源更优先的类别胜出。字典输入顺序不影响结果。
5. 融合分数使用**原始加权和，不按成功来源重新归一化**。因此某来源失败后，其他来源权重不会被放大；Embedding 和 Pattern 单独成功时理论最高分是 `0.20+0.10=0.30`，低于默认 `0.35` 阈值，默认设置下它们不能单独决定最终意图。这是保留 LLM 主导权的保守降级策略。
6. 若 `failure_policy="other"` 且任意启用来源没有有效候选，直接返回 OTHER/0/FALLBACK；若为默认 `available_sources`，继续用其余有效来源投票。若没有任何有效候选，返回 OTHER/0/FALLBACK。
7. 若最高累计分低于 `confidence_threshold`，返回 OTHER，confidence 保留最高加权分用于观察，source 为 FALLBACK；达到阈值（含等于）则返回获胜类别、累计分和贡献该类别的优先来源。

`source_scores` 保留每个启用来源的原始 confidence，不是加权后分数；缺失/无效来源记录为 0。被配置关闭的来源不写入该映射。融合结果 confidence 是获胜类别的加权累计分，最大限制为 1。

### 计算示例

输入三个候选：LLM 判退款 `0.80`，Embedding 判退款 `0.90`，Pattern 判物流 `0.90`。按默认权重：

```text
REFUND = 0.70*0.80 + 0.20*0.90 = 0.74
LOGISTICS = 0.10*0.90 = 0.09
```

REFUND 获胜且 `0.74 >= 0.35`，结果为 `IntentResult(intent=REFUND, confidence=0.74, source=LLM, source_scores={"llm":0.80,"embedding":0.90,"pattern":0.90})`。LLM 是 REFUND 的支持来源中优先级最高者，因此最终 source 为 LLM。

降级示例：LLM 调用失败表现为 `OTHER/0`，Embedding 和 Pattern 都判物流 `0.90`：`LOGISTICS = 0.20*0.90 + 0.10*0.90 = 0.27`。默认 `available_sources` 下继续投票，但 `0.27 < 0.35`，所以结果是 OTHER、confidence `0.27`、source FALLBACK。若把失败策略改成 `other`，检测到启用来源 LLM 没有有效候选后立即返回 OTHER/0。

### 使用方式与上下游

```python
from core.config import IntentSettings
from core.intent import IntentSource
from core.intent_embedding import IntentEmbeddingMatcher
from core.intent_fusion import combine_intents
from core.intent_llm import IntentLLMClassifier
from core.intent_pattern import recognize_pattern

llm_candidate = await IntentLLMClassifier(llm).recognize(message)
embedding_candidate = IntentEmbeddingMatcher.from_env(settings).recognize(message)
pattern_candidate = recognize_pattern(message).candidate
result = combine_intents({
    IntentSource.LLM: llm_candidate,
    IntentSource.EMBEDDING: embedding_candidate,
    IntentSource.PATTERN: pattern_candidate,
}, settings.intent)
```

- **上游**：LLM 分类器返回异步候选，Embedding matcher 和 Pattern matcher 返回同步候选；三者都遵循 `IntentCandidate`。
- **本次**：仲裁器接收三路结果和 `IntentSettings`，输出 `IntentResult`。
- **下游**：`IntentResult.to_state()` 可供后续会话 state 持久化和 Agent 路由使用；本次没有接入 `/chat`，也没有调用三路分类器本身。
- `tests/test_intent_fusion.py` 覆盖三路一致、冲突、来源失败、阈值拒绝、严格失败策略、禁用来源、平分优先级和非法候选。

## 今天第八件事：将意图结果写入短期记忆 state

完成 `feat(core): persist intent state in short-term memory`。在 `memory/service.py` 的 `ConversationMemory` 新增 `persist_intent(user_id, session_id, result)`，把三路融合后的 `IntentResult` 保存到该用户该会话的 Redis state。这个方法提供持久化能力，但本次没有调用识别器、没有接入 `/chat`，也没有自动决定在哪一轮调用；未来聊天链路应在成功获得融合结果后显式调用。

### 输入、写入结构和输出

- 输入 `user_id`、`session_id` 用于定位现有会话 state；输入 `result` 必须是 `IntentResult`，否则抛 `TypeError`。
- 通过 `result.to_state()` 序列化，存到 state 字典的 `intent` 字段下。字段包括最终 `intent` 字符串值、`confidence`、`source`、`source_scores`、`entities` 和 `reasoning`。例如概念上的 state 为：

```json
{
  "stage": "refund_pending",
  "intent": {
    "intent": "refund",
    "confidence": 0.91,
    "source": "llm",
    "source_scores": { "llm": 0.9, "embedding": 0.8, "pattern": 0.0 },
    "entities": { "order_id": ["A-123"] },
    "reasoning": "用户询问退款进度"
  }
}
```

- 返回 `None`；写入后可通过既有 `store.get_state(user_id, session_id)` 或 `read_context()` 读取。每次调用以新 `IntentResult` 整体替换 `state["intent"]`，因此保存的是当前最新识别结果；state 中的 `stage`、槽位等其他字段会保留。

### 写入流程及并发、TTL 行为

1. 校验 `result` 类型，避免随意对象绕过统一结果结构。
2. 获取 RedisMemoryStore 已有的该 `user_id + session_id` 会话锁，避免与同会话的聊天提交/其他意图 state 更新同时读改写。
3. 读取当前 state；如果 key 不存在或已过期，store 返回 `{}`。
4. 仅替换 `state["intent"]`，其他 state 字段原样保留。
5. 调用现有 `set_state()` 将完整 state JSON 写回 Redis。写入按现有 TTL 使用 `SETEX`，会刷新该 state 的过期时间；用户或会话不同，Redis state key 不同，互不覆盖。
6. state 到期后 Redis 删除 key，后续读取得到 `{}`，其中意图也随 state 一起清理。已有 working memory/summary 的 TTL 不因单独写 intent 被改变。

使用示例：

```python
from core.intent import IntentCategory, IntentResult, IntentSource

intent_result = IntentResult(
    intent=IntentCategory.REFUND,
    confidence=0.91,
    source=IntentSource.LLM,
    source_scores={"llm": 0.91, "embedding": 0.0, "pattern": 0.9},
    entities={"order_id": ["A-123"]},
    reasoning="用户询问退款进度",
)
await memory.persist_intent("customer-7", "session-abc", intent_result)
state = await memory.store.get_state("customer-7", "session-abc")
print(state["intent"]["intent"])  # refund
```

### 上下游与验证

- **上游**：未來整合层用 `combine_intents()` 得到 `IntentResult`，并在选定的成功处理时机传给 `persist_intent()`。本次没有把候选或单路结果直接写入 state。
- **本次**：ConversationMemory 负责会话定位、锁内合并、JSON 序列化委托和 Redis TTL 写入；不负责识别，也不负责解析 state 内容。
- **下游**：后续轮次可从 `MemoryContext.state["intent"]` 读取最新意图，供追问解析或 Agent 路由；当前对话逻辑尚未消费该字段。
- 新增 `tests/test_intent_state.py` 覆盖同会话多轮更新、保留其他 state 字段、用户和会话隔离、TTL 刷新、过期清理及错误输入。

## 今天第九件事：在 `/chat` 中识别并保存意图

完成 `feat(api): expose intent recognition in chat flow`。`/chat` 在意图总开关 `COMMERCEMIND_INTENT_ENABLED=true` 时：读会话记忆、识别当前轮意图、生成回答、成功后将本轮 turn 与更新后的 state 一起提交。开关默认关闭，所以不配置时保留旧请求耗时和 API 行为。响应 JSON 未增加意图字段，意图通过记忆 state 留存。

### 请求内执行顺序

1. 按原逻辑解析会话、处理幂等回放、取得会话锁并读取历史/state。命中已提交的幂等回执时直接回放，不重复识别，也不修改 state。
2. 将已读取的 state 作为当前会话状态基底；历史消息保留用于模型上下文。旧 state 是当前轮的上下文，不与新识别分数做数学合并；本轮 `IntentResult` 替换 state 中的最新 `intent` 字段，其他业务状态字段保留。
3. 只有 `settings.intent.enabled` 为 true 才识别。`_recognize_intent()` 根据三个单路开关启动对应路径：LLM async；Embedding 与 Pattern 同步方法放入 `asyncio.to_thread()`，避免同步计算/HTTP embedding 阻塞事件循环。启用来源通过 `asyncio.gather(..., return_exceptions=True)` 并发执行，单路异常不会直接中断聊天链路。LLM 分类器接收最近五条对话 history；Embedding 和 Pattern 仍只检查当前消息。
4. PatternMatch 转成内部 `IntentCandidate`；另外两路本来就返回候选。调用 `combine_intents()` 按设置权重、阈值和失败策略得到 `IntentResult`。
5. 只有三路融合完成后，把读取到的 state 复制并更新 `state["intent"] = result.to_state()`，保留 stage、槽位等其他字段。
6. 然后调用聊天 LLM 生成回答。聊天模型调用失败时走原错误处理；识别虽已发生，但 turn 和新 state 都不会提交，Redis 中仍是上一轮成功提交的 state。
7. 回答成功后，在同一 `memory.commit(..., lock_held=True, state=state)` 中提交回答 turn 与新 state。store 使用同一个 Redis MULTI/EXEC 写 working turn 和 state，不会出现 turn 已存而意图单独先写入的部分成功。
8. 意图识别内部异常不会中断回答；日志记录识别异常，沿用旧 state 并正常生成回答。若 state 读取失败则不传 state，避免用不完整数据覆盖 Redis。若 turn/state 提交失败，回答仍返回，记忆提交失败记录 warning。

### 配置、输入输出与 API 兼容

- 主开关默认 `false`；打开后仍可分别关闭 LLM、Embedding、Pattern。其权重、阈值和 `failure_policy` 沿用 `IntentSettings`。
- 三路都接收本轮 `req.message`；LLM 额外接收最近五条对话 history，Embedding 与 Pattern 不接收 history。当前旧意图不会被拼进新意图的数值投票；它保留在 state 里直到本轮识别成功并形成新 state。
- **三路识别各自的消息来源**：
  - **LLM**：来源是本轮 `req.message`，并附带从刚读出的 working memory 取最近五条消息作为 `history`。现有 `LLMClient.chat()` 按历史顺序发送这些 user/assistant 消息，最后追加当前用户消息；意图分类 prompt 让模型结合上下文判断当前轮主要意图。
  - **Embedding**：来源只有本轮 `req.message`。matcher 将这条文本编码成 query vector，与内置意图示例模板向量比较。
  - **Pattern**：来源只有本轮 `req.message`。规则匹配器在当前文本上查关键词。
  - 三路的当前输入都来自同一个 HTTP 请求 `ChatRequest.message`；区别是只有 LLM 会额外收到最近五条 working-memory 消息。三路分别产出候选后才由融合器合并，旧 state 不作为第四路候选。
- 融合器输出 `IntentResult`，state 保存 intent 值、confidence、最终来源、各来源原始分数、entities、reasoning。`ChatResponse` schema 没变，客户端仍只看到 request/session、answer、latency 和 token usage。
- 关闭意图总开关时不会发额外模型调用，不会修改本轮传给记忆提交的 state 参数，行为与原链路一致。
