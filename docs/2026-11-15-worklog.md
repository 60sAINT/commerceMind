# 2026-11-16 工作日志：把聊天主链路切换为 SSE 流式

今天把聊天入口统一为 `POST /chat/stream`，移除旧的 `POST /chat` JSON 聊天路由和前端 JSON 降级调用。下面按一次请求实际发生的先后顺序记录当前实现；工作区改动未提交。

## 正常请求流程

1. **前端发起请求。** `chatStore.send()` 创建并保存用户气泡及新的 `client_request_id`，`streamChat()` 用 `fetch` 向 `/api/chat/stream` 发送 POST JSON，携带 `user_id`、当前 `session_id`、消息和请求 ID，并设置 `AbortSignal`。
2. **后端校验与准备。** FastAPI 校验 `ChatRequest`、确认模型已配置，解析手动/自动 Skill 选择并组装 Skill system 文本。此阶段错误以普通 HTTP JSON 返回；SSE 尚未开始。后端按 `client_request_id` 查成功回执，命中时校验消息正文并准备回放；同 ID 不同正文返回 409。
3. **建立流与会话。** 后端发送 `meta`，包含执行 `request_id` 和 `session_id`。前端收到 meta 后立即将首次会话从临时 key 迁移到后端 session key，后续消息留在当前会话。
4. **锁定并读取记忆。** 有记忆服务时，后端取得该会话锁并再次查回执，避免并发请求重复生成。未命中回执则读取 `MemoryContext`：其中包含 working memory 的历史消息、summary 和 state。读取上下文失败会降级为无历史继续生成，并尝试单独读取 state。
5. **意图识别。** `COMMERCEMIND_INTENT_ENABLED` 开启时，后端用当前消息和最近 5 条历史做已启用识别源的分类，再由 `combine_intents()` 融合结果。融合结果写入待提交的 `state["intent"]`；识别异常只记录 warning，不阻断回答。此处不会单独提前写 Redis。
6. **组装模型输入。** working memory 的历史消息作为 LLM `messages` 的 history 参数；summary 由 `MemoryContext.to_system_text()` 序列化后并入 system 文本；当前用户消息作为本轮 user message。Skill system 也进入 system 文本。若本轮意图识别成功并生成待提交 state，完整 state（含融合后的 intent）会以 JSON 形式追加到 system 文本，并明确标注为历史参考数据、不是指令；该 state 同时在本轮成功提交时持久化。
7. **流式生成。** `LLMClient.stream_chat()` 调用 Anthropic 兼容接口的 streaming API。后端逐段收到文本后追加到服务端缓冲区，并发 `delta` SSE；前端通过 `ReadableStream` 解析事件，把 delta 暂存到下一帧，用 `requestAnimationFrame` 合并更新助手气泡。
8. **完成与提交。** 上游正常结束且完整文本非空后，后端先发 `done`。前端收到 done 时立刻把用户消息和助手回答置为完成并锁定，不等 HTTP body 关闭。随后后端调用 `memory.commit()`；Redis 原子提交完整 turn、成功回执、working memory 和本轮 state，并排队触发异步 summary/长期记忆维护。无记忆配置时跳过记忆提交。

回执回放也走 SSE：发送 `meta`、包含完整历史答案的 `delta`、`done`，不再调用模型或再次提交记忆。

## 前端按终止键

1. 前端立即 abort fetch、取消 reader，并将用户消息从 pending 改为可重试的中断状态；已经收到的助手片段保留为 `interrupted` 展示项，但不参与后续后端上下文。
2. 服务端/ASGI 收到断连后取消流任务；取消沿 `LLMClient.stream_chat()` 传递并关闭上游 stream。会话锁通过 shield 清理续租任务并释放 Redis 锁。
3. 若断开发生在生成完成、`done` 发出之前，正常取消路径不会调用 `memory.commit()`，所以不写半轮和成功回执。用户原文重试复用同一个 `client_request_id`；编辑后正文改变则生成新 ID。
4. 边界：如果断开与 done/commit 竞态，或者 done 已发出后前端才终止，后端可能已经进入提交，前端取消连接不能回滚已提交的 turn。UI 的终止只能确定停止本地接收；服务端结果以回执为准。

## 已提交后遇到网络问题并重试

1. 如果完整 turn 和成功回执已经写入 Redis，但 `done` 或后续网络数据未可靠到达前端，前端保留这条消息及原 `client_request_id`，将未知结果作为可重试状态处理。
2. 重试仍请求 `/chat/stream` 并携带相同 ID、相同正文。后端通过用户级回执索引恢复原 session，再从会话回执读取 turn；正文一致则回放原完整答案为 `meta + delta + done`，不重新调用 LLM、不重复写 working memory/state/回执。
3. 同 ID 不同正文返回 `client_request_id_conflict`。编辑后必须使用新 ID。
4. 如果前次只发了 done、但记忆提交失败，则没有成功回执；同 ID/同正文重试会再次执行模型并尝试提交。未来若 Agent 调用有外部副作用的工具，必须另做工具级幂等，避免重跑副作用。

## 本次改动覆盖的流程部分

- 后端把 LLM 一次性 `chat()` 调用改成 `stream_chat()`，增加 `/chat/stream` SSE 事件传输；短期记忆读取、意图识别、融合 state、state prompt 注入和成功提交接入流式路径。
- 前端把请求传输、事件解析、增量 UI、done 锁定、取消与重试接入原会话状态机；删除 HTTP chat 和 404 JSON 降级路径。
- 新增异步请求锁的取消清理，避免断连后会话锁残留。
- 未改变 Redis turn/receipt 的数据结构和 `commit_turn` 原子写入实现；本次选择 done 先于 commit，故提交失败时允许同 ID 重跑。

## Session PostgreSQL 持久化与接口

- Compose 新增 PostgreSQL 16 服务和 `postgres_data` 持久卷，配置 `DATABASE_URL`；容器数据目录为 `/var/lib/postgresql/data`。
- `api/sessions.py` 在应用启动时建 `sessions`、`session_messages` 表和分页/幂等索引。`session_id` 是产品会话主键，完整 user/assistant 内容长期保存在 PostgreSQL；Redis 仍用于模型工作记忆、state、summary、会话锁和短期回执。
- 新增 `POST /sessions` 创建 session、`GET /sessions` 按 user 分页取列表、`GET /sessions/{session_id}/messages` 取消息页、`DELETE /sessions/{session_id}` 删除 session；按 `user_id + session_id` 校验归属。
- `POST /chat/stream` 命中 PostgreSQL 幂等记录时直接 SSE 回放。新回答完整生成后先用 PostgreSQL 单事务保存 user/assistant 消息、session 元数据和同 ID 回执；事务成功后更新 Redis 记忆，最后发送 `done`。PostgreSQL 提交失败发送 `error`，不发送成功 `done`；Redis 记忆维护失败只记日志，持久历史保持有效。
- 前端 `services/sessions.ts` 提供创建、列表、分页取消息和删除 API；`types/api.ts` 增加 session DTO。

## 前端：把流式输出接进状态层

`frontend/src/services/chat.ts`（修改）用原生 `fetch` 请求 `/chat/stream`，逐行解析 SSE：

- `meta` 立即确定后端 session；
- `delta` 用 `requestAnimationFrame` 合并刷新，避免每个 token 都触发一次渲染；
- `done` 到达即锁定本轮，不等待 HTTP 连接关闭；
- 非 2xx 与 `error` 事件统一转成 `ApiError`，带上 `status`、`error_code`、`request_id`。

`frontend/src/stores/session.ts`（新增）保存 `userId`、`sessionId`、`baseUrl`、`theme`，用 zustand `persist` 写入 `localStorage`，刷新后保留当前会话和深色主题。

`frontend/src/stores/chat.ts`（新增）按 `sessionId` 保存 `messagesBySession`，并负责整条流式状态机：

- `send`：先插入用户消息，再调用 `streamChat`；`meta` 到达后把临时会话迁移到后端返回的 `session_id`。
- `retry` / `editAndResend`：只允许对失败的用户消息重试；正文未改时复用原 `client_request_id`，改动后生成新 ID。发起前用 `dropStreamArtifacts()` 按 `requestId` 清掉上一轮的 `stream-*` / `partial-*`，避免新旧回答叠加。
- `stop` / `cancelForSessionSwitch`：abort 当前 fetch，并通过 `settleInterruptedStream()` 收尾——有内容的 `stream-*` 改名为 `partial-*` 并标记 `interrupted: true`，保留已经生成的文字；只有还没收到任何文字的空占位才丢弃。`partial-*` 只用于展示，不参与后续请求的后端上下文；用户消息标记为可重试错误，保留“重试 / 编辑”入口。
- `clear` / `remove`：前者清空消息，后者删除 `messagesBySession` 的整个 key，避免空数组被侧栏渲染成“新会话”。
- `activeController`、`activeRequestId`、`sendingSessionId` 共同防止旧请求回写新会话。

`frontend/src/App.tsx`（修改）把上述状态接成界面：会话侧栏、新建/切换/删除会话、消息列表、编辑重发、重试、中断、输入框、主题切换，以及 `/health` 连接探针。中断后的助手片段下方显示一行浅色“已中断”；删除当前会话后切到剩余历史的最后一条，没有历史则回到真正的空白新会话。`App` 用稳定的 `EMPTY_MESSAGES` 常量替代 `?? []`，避免滚动 effect 的依赖每次渲染都变化。

测试覆盖：

- `tests/test_chat_api.py`：新增 SSE 事件顺序用例，确认 `meta` / `delta` / `done` 和替身模型只调用一次。
- `tests/test_chat_memory.py`：`FakeLLM` 增加 `stream_chat`；覆盖成功轮次提交后 `state.intent` 为识别结果且 SSE 响应体不含意图字段，以及识别执行过但生成失败时 state 和 turns 都不写入。
- `tests/test_memory_store.py`：覆盖 anyio 取消下 Redis 锁仍会释放。

真实链路：

- 客户端断连 1s 后，Redis 中没有残留的 `lock:conversation:*`。
- 同一 `client_request_id` 重试，1.1s 内开始返回 `delta` 并最终 `done`；再次请求直接回放回执。
- 同会话发送新消息，正常收到 `delta + done`。
- 浏览器中断 1200 字生成后保留约 430 字片段并显示“已中断”；重试可正常完成，再发新消息 1.3s 内收到回答。
- 临时容器开启 pattern-only 意图识别：stream 返回 `done` 后，Redis 的 `state_v1:*` 中出现 `intent` 字段。

## 已知限制

- 旧 `/chat` 的 24 个测试仍在跑已移除的路由，当前是 `24 failed, 16 passed`；这些用例还没迁移到 SSE 协议。
- `done` 先于记忆提交发出：如果提交失败，前端仍保留完整回答，但服务端没有成功回执，后续同 ID/同正文重试会重新生成。未来接入有副作用的工具调用时，需要单独做幂等保护。
- 流式取消依赖 ASGI 的断连传播和上游 stream 关闭；部署时必须关闭代理缓冲，并保留 `X-Accel-Buffering: no`。
- 意图识别仍由 `COMMERCEMIND_INTENT_ENABLED` 控制，当前 `.env` 未开启时不会执行。
