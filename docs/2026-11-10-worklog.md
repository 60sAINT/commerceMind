### 怎么把 DeepSeek tokenizer 接入项目

1. 下载官方 tokenizer 包：

   ```text
   https://cdn.deepseek.com/api-docs/deepseek_v4_tokenizer.zip
   ```

2. 解压后把 `tokenizer.json`、`tokenizer_config.json` 放到 `memory/tokenizer/deepseek-v4/`；`source.json` 记录下载地址和 sha256。
3. 安装依赖：`tokenizers==0.20.3`、`Jinja2==3.1.6`。
4. 加载 tokenizer：`Tokenizer.from_file(...)`，关闭 truncation 和 padding。
5. 从 `tokenizer_config.json` 读取 `chat_template`，用 Jinja2 渲染消息列表。
6. 渲染时传 `add_generation_prompt=False`，再统计编码后的 token ID 数：

   ```python
   working_tokens = len(tokenizer.encode(rendered).ids)
   ```

7. `working_tokens >= 10_800` 时触发压缩。

### 计算范围

包含：每条消息正文、角色和分隔符、工具调用和工具结果。

不包含：旧 summary、system prompt、用户画像、长期记忆、Redis 时间戳/request_id 等元数据。

不额外加 4 tokens/message，也不用“汉字数 × 系数”。

## 今天第二件事：实现按轮存储的 Redis 短期记忆

新增短期记忆的数据结构、Redis 读写工具和会话锁。可以把它们理解成：`models.py` 定义“记录长什么样”，`store.py` 负责“存取记录”，`locks.py` 负责“多人同时存时排队”，测试文件负责“检查是否符合预期”。

文件本身叫模块，不是单个函数。模块里可以定义类、数据结构和函数；类上提供的方法，就是这个对象能执行的操作。

### 1. `memory/models.py`：定义一轮问答和读取结果的数据结构

这里主要是两个数据类，只在 Python 内存中组织数据，自己不会连接 Redis、生成回答或算 token。

| 数据类 / 方法                  | 输入                                                           | 输出与用途                                                                                                                     |
| ------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `Turn(...)`                    | 请求编号、用户问题、assistant 回答，可选轮次编号、时间和元数据 | 一个“完整问答”对象；未提供轮次编号和时间时自动生成，问题/回答不能为空                                                          |
| `Turn.to_json()`               | 已有的 `Turn` 对象                                             | JSON 字符串，交给 store 存入 Redis；一轮只占一个 List item                                                                     |
| `Turn.from_json(raw)`          | 从 Redis 取出的 JSON 字符串                                    | 还原为 `Turn` 对象                                                                                                             |
| `Turn.to_messages()`           | 已有的 `Turn` 对象                                             | 两条消息的列表：先 user、再 assistant，供 tokenizer 或后续模型上下文使用                                                       |
| `MemorySnapshot(...)`          | 多个 `Turn`、业务状态字典 `state`、摘要字符串 `summary`        | 一份读取结果对象，方便调用方一起拿到三类数据；第三件事中已将 store 的读取升级为同一 Redis 事务，避免轮次与摘要来自不同读取时点 |
| `MemorySnapshot.to_messages()` | 已有的读取结果对象                                             | 把所有轮次展开成按时间排序的消息列表，不把 state 和 summary 混进去，交给 `TokenCounter` 计数                                   |

例如一轮 `Turn(user_message="何时发货？", assistant_message="请提供订单号。", request_id="r1")`，转成消息后就是：

```python
[
    {"role": "user", "content": "何时发货？"},
    {"role": "assistant", "content": "请提供订单号。"},
]
```

辅助函数 `utcnow()` 无需输入，返回带 UTC 时区的当前时间。两个数据类的 `__post_init__()` 在创建时自动检查字段，非法输入会报错。

### 2. `memory/store.py`：真正读写 Redis 的工具类

主要类是 `RedisMemoryStore`。上游由后续 manager 提供用户、会话和问答内容；下游是 Redis，以及需要读取历史的 context / 后台维护流程。

| 方法                                                               | 输入                                                                         | 输出与用途                                                                                                                                                 |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RedisMemoryStore(client, ttl_s=...)` / `from_url(url, ttl_s=...)` | Redis 客户端或连接地址，可选保存时长                                         | 一个存储工具对象；默认 TTL 为 7 天，TTL 指数据多久不续期就自动过期                                                                                         |
| `commit_turn(...)`                                                 | 用户 ID、会话 ID、请求编号、问题、回答；可选成功标记、state、summary、元数据 | 成功返回已保存的 `Turn`；`succeeded=False` 返回 `None` 且不写入。事务中追加完整一轮及可选状态/摘要，并刷新相关 key 的 TTL；未传 state/summary 时保留已有值 |
| `get_turns(user_id, session_id, limit=...)`                        | 用户、会话，可选最近轮数                                                     | `list[Turn]`，按旧到新排序；不传 limit 时读全部                                                                                                            |
| `get_snapshot(user_id, session_id, limit=...)`                     | 同上                                                                         | `MemorySnapshot` 对象，包含轮次、state 和 summary，供后续维护/上下文组装使用                                                                               |
| `get_state(...)` / `set_state(..., state)`                         | 用户、会话；写入时额外传字典                                                 | 读取返回状态字典，没有则 `{}`；写入无业务返回值，更新状态及自身 TTL                                                                                        |
| `get_summary(...)` / `set_summary(..., summary)`                   | 用户、会话；写入时额外传摘要字符串                                           | 读取返回字符串，没有则空字符串；写入无业务返回值，更新摘要及自身 TTL，不负责生成摘要                                                                       |
| `close()`                                                          | 无额外参数                                                                   | 无业务返回值，关闭 Redis 客户端连接                                                                                                                        |

内部还有 `session_key_id()` 和三个 `*_key()` 方法：输入用户/会话，输出哈希标识或 Redis key，隔离不同会话；`_json()` 把数据转为 JSON；`_session_lock()` 在提交期间调用下面的锁。业务调用方通常只调用公开读写方法，不用自己拼 key 或加锁。异步读写方法调用时使用 `await`。

### 3. `memory/locks.py`：提交前先排队，防止同一会话并发写入互相干扰

这里既有类也有函数，主要由 store 内部使用，不保存聊天内容。

| 类 / 函数                                          | 输入                                   | 输出与用途                                                                                                   |
| -------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `KeyedLocks()`、`hold(key)`                        | 创建时无参数；进入锁时传会话标识       | 提供 `async with` 使用的锁定区间，没有业务数据输出；同一个 Python 进程中同一会话依次执行，不同会话可分别处理 |
| `redis_lease(client, key, wait_s=30, lease_s=120)` | Redis 客户端、锁 key、等待和租期秒数   | 提供跨进程的 `async with` 锁定区间；获取成功后才执行内部代码，期间后台续租，退出后尝试释放自己的锁           |
| `LockBusyError` / `LeaseLostError`                 | 无需业务代码主动传入；遇到异常情况抛出 | 两个异常类，分别表示等待锁超时、持有期间续租失效；后者会中止持有者任务，提醒调用方停止继续写入               |

`redis_lease()` 内部的 `extend()` 返回续租是否成功，`renew()` 定期续租，`release()` 释放锁，均不需要外部传参。锁的创建、续租和释放由 store 自动组织；它不等于“已经实现请求幂等”，同一请求重复提交的去重仍留给后续步骤。

### working memory 怎样变成 summary：用 LLM，总共一次或两次调用

`TokenCounter` 只负责计数，不会写摘要。真正总结内容的是注入给 `MemoryCompactor` 的摘要函数。正常使用时传 `llm.summarize`，测试时换成 fake 函数，所以测试不产生模型请求。

**第一步：取出要压缩的旧消息。** `get_snapshot()` 用一个 Redis 事务读取当前轮次、state 和旧 summary。Python 中的 `snapshot.turns` 按旧到新排列；`snapshot.turns[:-2]` 取出最后两轮之前的所有旧轮次，再调用各轮的 `to_messages()` 展开成 user/assistant 消息列表。

例如已有 T1～T6 六轮：

```text
T1、T2、T3、T4 → 展开成 8 条消息，参与本次摘要
T5、T6         → 最近 4 条消息，不参与摘要，也不裁剪
```

**第二步：第一次调用 LLM，生成新增摘要。** 把上面的旧消息列表转成 JSON 字符串，拼进提示词，要求保留用户目标、已确认事实、约束、已执行动作、未解决问题，只输出简洁中文摘要。JSON 只是方便传递历史数据，并不是用 JSON 算法自动生成摘要。模型返回的是普通摘要字符串。

```text
旧消息列表 → JSON 文本 + 总结提示词 → llm.summarize(prompt) → 新增摘要
```

**第三步：如果已有旧 summary，再调用一次 LLM 合并。** 第二次提示词携带两个字段：

```json
{
  "old_summary": "Redis 中原有的摘要",
  "new_summary": "第一次模型调用生成的摘要"
}
```

要求模型保留关键信息、去除重复，输出合并后的摘要。不是直接字符串拼接覆盖，也不会再次把 T5、T6 的原文发过去。没有旧 summary 时跳过合并，直接使用新增摘要：

```text
无旧 summary：旧消息 → LLM → 最终摘要                         （一次调用）
有旧 summary：旧消息 → LLM → 新增摘要；旧摘要 + 新增摘要 → LLM → 最终摘要（两次调用）
```

`LLMClient.summarize()` 通过现有 `AsyncAnthropic` 客户端请求模型，复用 `Settings` 中配置的模型、API 地址、Key、单次超时和输出上限。因此摘要会调用配置的 LLM；如果应用配置为 DeepSeek，就请求对应的 DeepSeek 接口，并不是调用本地 tokenizer 来生成摘要。它与日常 `chat()` 使用不同的 system 指令，但复用底层 `_generate()` 和错误处理。

当前 compactor 一次操作总超时默认 30 秒；每次模型调用另受 `Settings.timeout_s` 限制。模型调用报错、返回空摘要、输出因 `max_tokens` 被截断，或第二次合并失败时，流程结束，不继续执行历史删除，也不把半成品摘要写入 Redis。

### 合并后的 summary 怎样写入 Redis，working memory 怎样裁剪

摘要生成期间只在 Python 内存中保存结果，不先改 Redis。全部生成成功后，才调用 `store.commit_compaction(..., snapshot=snapshot, summary=最终摘要)`。

这里**没有把 working memory 整个清空后重写**，而是在 Redis 原列表上用 `LTRIM` 保留指定部分。两个数据分别保存：

| Redis key               | 数据类型 | 存什么                                  |
| ----------------------- | -------- | --------------------------------------- |
| `wm_v1:{会话哈希}`      | List     | 一轮一个 JSON item，最新在列表头部      |
| `summary_v1:{会话哈希}` | String   | 合并后的摘要正文，覆盖此 key 中的旧摘要 |

提交前先 `WATCH` 上面两个 key，再读当前内容，确认旧 summary 没变、快照中的原轮次仍完整存在。只在头部新增轮次是允许的；旧内容被修改/裁剪、摘要已被其他任务更新或原数据已过期，则放弃本次提交。

检查通过后，按下面的数量保留列表头部：

```python
keep_count = 当前轮次数 - 原快照轮次数 + 2
```

例如快照有 T1～T6，摘要期间新增了 T7，此时 Redis 中从头到尾为：

```text
裁剪前：[T7, T6, T5, T4, T3, T2, T1]  # 最新在前
keep_count = 7 - 6 + 2 = 3
LTRIM key 0 2
裁剪后：[T7, T6, T5]                  # 保留新增 T7 和原本保护的 T5、T6
```

没有新增轮次时就只保留 T5、T6。后续读取会反转为旧到新，调用方得到 T5、T6、T7 的顺序。

写入和裁剪放在同一个 `MULTI/EXEC` 事务中执行，其他命令不能插入这些操作之间：

```text
SETEX summary_key TTL 最终摘要       → 更新摘要，并设置过期时间
LTRIM working_key 0 keep_count-1    → 原地删除已被摘要覆盖的旧轮次
EXPIRE working_key TTL             → 刷新工作记忆 TTL
EXPIRE state_key TTL               → 已有 state 续期，不改业务状态内容
EXEC
```

TTL 使用 store 配置，默认 7 天。如果在 `WATCH` 后到 `EXEC` 前 key 被其他任务修改，Redis 拒绝该次受监视事务，代码重新检查，最多尝试 3 次；持续冲突就跳过，留待以后维护。生成期间新追加的轮次不会被当作旧消息裁掉。

### 两层会话锁分别锁什么，和 WATCH 有什么区别

两层锁嵌套在 `store._session_lock()` 中，当前只包住 `commit_turn()` 的问答提交阶段。锁的身份来自 `user_id + session_id`：同一用户、同一会话排队，不同会话使用不同锁。

| 机制                                   | 保护范围                                                                   | 当前在哪里使用                                            |
| -------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------- |
| 第一层 `KeyedLocks.hold(digest)`       | 同一 store 实例复用的进程内锁，让本进程同会话的提交依次进入                | `commit_turn()` 外层，先本地排队，减少争抢 Redis 锁       |
| 第二层 `redis_lease(client, lock_key)` | 多个 Python 进程或 store 实例之间，共用同一 Redis 锁 key 时互斥            | 本地锁内再获取 Redis 租约，持有期间才提交问答；退出后释放 |
| `WATCH/MULTI/EXEC`                     | 不是上述两层中的又一把排队锁；它检查“读取之后数据有没有变”，冲突时拒绝事务 | 压缩最终提交，保护新摘要和历史裁剪不使用失效快照          |

Redis 租约通过 `SET NX PX` 获取：锁不存在才写入，且带过期时间。默认最多等 30 秒，租期 120 秒，持有期间约每 40 秒续租；释放前检查随机持有者标记，避免删掉别人的锁。这个随机标记与 LLM 的 token 计数没有关系。等待超时报 `LockBusyError`；持有期间续租失效会取消持有者任务，并报告 `LeaseLostError`。

**压缩不会在调用 LLM 的几十秒期间占着上述两层会话锁。** `compact()`、`commit_compaction()` 没有进入 `_session_lock()`，而是依靠快照检查和 WATCH 条件提交，因此摘要期间 `commit_turn()` 仍可保存新问答。`get_snapshot()` 的事务只负责一次读取一致，也不是持有整个摘要过程的锁。

`compactor.start()` 另外会在同一个 compactor 对象内复用同会话尚未完成的 Task，减少重复摘要；这只是本地任务去重，不是跨进程锁。多个实例仍可能同时生成摘要，但条件提交会阻止已失效的压缩结果覆盖当前数据。`set_state()`、`set_summary()` 独立写接口也没有自动获取这两层锁；其中 summary 的变化会让进行中的压缩提交检查失败。

所以目前不是“同会话整个 `/chat` 已被串行化”：会话锁保护的是问答落库，WATCH 保护的是压缩结果提交；完整聊天流程及后台调度接入仍在后续步骤。

### 固定处理流程

```text
ContextBuilder → 读取全部 working memory + summary，交给后续聊天调用方
成功问答落库 → 调用 compactor.start(user_id, session_id)
    → 对完整 working memory 计数
    → 不足 10,800：结束
    → 达到阈值但只有两轮或更少：跳过，没有可压缩的旧轮次
    → 只把最近两轮之前的消息送给摘要函数
    → 有旧 summary 时再调用模型合并摘要
    → 全部成功：条件提交新 summary，删除已摘要旧轮次
```

最近 **4 条消息（2 个 Turn）既不送入摘要，也不被裁剪**。摘要期间新增的所有轮次同样保留。模型失败、超时、空摘要或合并失败都不提交删除；检测到旧历史/摘要已被其他任务修改、数据过期或持续 WATCH 冲突则跳过提交，不覆盖或复活旧数据。摘要过程中不持有会话锁，因此新的问答可以继续保存。

后续调用示意（在异步函数中；store 和 llm 由调用方创建）：

```python

# 后续模型调用使用 messages/system；成功后 await store.commit_turn(...)

# 服务退出时先 await compactor.close()，再关闭 store/模型客户端
```

### 什么时候存情景记忆

不是每聊一句就写 Chroma，而是在一次后台压缩成功时，保存本次旧对话的新增摘要：

1. 一轮成功问答先写入 Redis working memory，再由调用方启动 `compactor.start(user_id, session_id)`。
2. 全部 working memory 达到默认 10,800 tokens，且存在最近两轮之前的旧轮次，才调用 LLM 生成新增摘要。
3. **被压缩的旧轮次默认至少两轮**才形成 episode。例如共 4 轮时压缩前 2 轮、保留后 2 轮，才满足此条件；共 3 轮时可压缩前 1 轮，但不形成 episode。
4. 若已有旧 summary，再调用 LLM 合并。只有 Redis 的快照检查及压缩提交成功，episode 才进入待写记录。模型失败、合并失败、并发冲突都不会留下本次 episode。

### 怎么存：先保证不丢，再写向量库

```text
旧消息 → LLM 生成 new_summary
           ├→ 与 old_summary 合并 → Redis 保存当前会话的累计 summary
           └→ 手机号/邮箱/身份证号脱敏 → Episode → Redis 待写 Hash
                                                     ↓
                                              embedding 生成向量
                                                     ↓
                                              ChromaDB upsert
                                                     ↓
                                              删除 Redis 待写项
```

- `Episode.from_turns()` 接收本次旧轮次与 `new_summary`，生成稳定 episode ID；用户、会话、起止轮次用 SHA-256 标识。脱敏发生在 embedding 调用前。
- Redis 的摘要更新、旧轮次裁剪和待写 episode 通过同一事务提交。待写 Hash 为 `memory:pending_episodes:v1`，field 是 episode ID，value 是脱敏 Episode JSON，无 TTL，避免向量库不可用期间记录过期丢失。
- 注入 longterm 后，压缩成功会调用 `flush_pending(store)` 尝试写入，默认每批最多处理 20 条。未注入时只留 Redis 待写记录；服务恢复后也可以手动重试，不需要再次调用摘要 LLM。
- `add_episode()` 用 embedding 把脱敏摘要变为浮点向量，再执行 `collection.upsert(ids, documents, metadatas, embeddings)`。同一压缩段使用稳定 ID，重复写入覆盖同一记录，不会无限新增。
- Chroma 写成功才确认删除 Redis 待写项；失败保留记录。后续统一维护器负责自动重试调度。本步不是分布式跨库事务，而是 Redis 待写记录加幂等写入。

### 我们的代码怎样使用 BAAI/bge-m3

**bge-m3 是“把文字变成一串数字”的 embedding 模型，不负责写 summary，也不是 ChromaDB 本身。** 摘要由配置的 LLM 生成；bge-m3 给摘要和当前问题分别生成向量，ChromaDB 再比较向量相似程度。

当前实现是 `memory/longterm.py` 中的 `SiliconFlowEmbedding` 调用**硅基流动托管 API**，没有下载 bge-m3 权重，也没有在本机或 Chroma 容器中运行 bge-m3。配置里的模型名只是告诉远程服务使用哪个模型，不会触发本地模型安装。

| 配置 / 方法                            | 输入                                      | 输出与作用                                                                                                  |
| -------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `LongTermMemory.from_env()`            | 已加载的环境变量                          | 创建长期记忆工具；`auto` 有 Key 时选 `siliconflow`，无 Key 时选 `default`；显式 `siliconflow` 缺 Key 会报错 |
| `SiliconFlowEmbedding.__call__(texts)` | 字符串列表，如 `["用户咨询运动鞋退货。"]` | HTTP 请求返回每段文字对应的浮点向量列表 `list[list[float]]`；按响应 index 恢复输入顺序，超时 15 秒          |
| `add_episode(episode)`                 | 已形成的 episode                          | 先脱敏，将摘要交给 embedding，再把摘要、向量和元数据一起 upsert 到 Chroma                                   |
| `search(user_id, session_id, query)`   | 用户、当前会话、问题                      | 问题先脱敏，用同一 embedding 模型编码后检索，返回筛选后的 `EpisodeMatch` 列表                               |

API 请求形状如下，Key 从 `SILICONFLOW_API_KEY` 读取，不写进文档：

```text
POST https://api.siliconflow.cn/v1/embeddings
Authorization: Bearer <Key>
```

```json
{
  "model": "BAAI/bge-m3",
  "input": ["用户咨询运动鞋退货。"],
  "encoding_format": "float"
}
```

代码只使用返回的 dense 浮点向量，没有实现 bge-m3 的 sparse 或 multi-vector 检索。写入与检索都会调用 embedding；单纯读取已有记录不需要调用它。

**目前已有的免费本地分支用的是另一个模型，不是本地 bge-m3：**

```dotenv
COMMERCEMIND_MEMORY_EMBEDDING_PROVIDER=default
```

此时 `DefaultEmbeddingFunction()` 在调用方 Python 进程中运行 Chroma 默认的 `all-MiniLM-L6-v2` 模型，首次使用需下载模型；不调用硅基流动 embedding API。显式设为 `default` 后，即使有 Key 也走此分支。**本地 bge-m3 尚未实现，不能把 provider 改成 `local` 就当作已经接入。** 这里的免费仅指本地 embedding 无服务 API 费，聊天和摘要的 LLM 调用是另一条链路。

不同后端/模型使用不同 collection，名称为 `episodic_` 加 embedding 标识哈希前 12 位；例如 API 分支标识为 `siliconflow:BAAI/bge-m3`，默认分支为 `chroma:all-MiniLM-L6-v2`。写入和查询必须使用相同模型；API 失败时不临时切换后端，切换配置也不会自动迁移旧向量。

### 什么时候取情景记忆

预期在**用户新问题到来、调用回答模型之前**查询一次：用当前问题找同一用户其他会话中的相关经历，再把命中的摘要作为额外背景交给回答模型。

```text
收到当前问题
    → 读取本会话 working memory + Redis summary
    → 用问题检索同用户、其他 session 的 episode
    → 将相关 episode 摘要作为额外历史背景
    → 调用回答模型
```

**这是后续接入时机，不是已经接入 `/chat` 的行为。** 当前 `ContextBuilder` 仍只读 working memory、summary 和 state；应用必须显式调用 `longterm.search()`。开启新 session 也不会不分相关性地加载该用户全部长期记忆。当前会话被排除，是为了避免与已有 summary 重复。

### 怎么取：问题也先变成向量，再筛选结果

```python
# 在应用启动层创建对象；应先统一加载配置环境。
longterm = LongTermMemory.from_env()
# 在异步聊天流程、模型回答前调用：
hits = await longterm.search(user_id, session_id, "之前咨询的运动鞋怎么退货？")
episode_texts = [hit.text for hit in hits]
```

`search()` 的输入是用户 ID、当前 session ID、问题字符串；输出是 `EpisodeMatch` 列表，每条有 `episode_id`、`text`、`score` 和 `metadata`。

处理顺序：问题脱敏 → 使用当前 collection 相同的 embedding 模型生成问题向量 → Chroma query → 用户/会话筛选 → 按相关性排序 → 去重 → token 限制。

- 只返回 `user_key` 与当前用户一致、`session_key` 与当前会话不同的记录；应用层还会二次核对。
- collection 使用 cosine 距离，代码分数为 `1 - distance`。默认过滤分数低于 0.55 的结果；分数不是“回答正确率”。
- 默认先取 12 个候选（配置 top-k 后取 `max(top_k × 4, 12)`），按 episode ID 和脱敏后的正文去重，最终最多返回 3 条。
- 返回文本以空行连接，默认总量不超过 600 tokens；截断的是本次返回副本，不修改 Chroma 中保存的完整摘要。
- 空问题或检索失败返回空列表，后续可按没有长期记忆继续回答。取情景记忆不调用摘要 LLM，但会使用 embedding 服务/本地模型。

### ChromaDB 是哪种数据库

ChromaDB 是**向量数据库**：既保存摘要正文和附带信息，也保存代表文字含义的浮点向量，支持“意思相近”的检索，以及按用户等 metadata 条件筛选。

ChromaDB 里，Collection（集合）​ 相当于一张表，每条数据（记录）​ 是表里的一行。API 中参数名用复数（ids、documents、metadatas、embeddings）是因为 Chroma 的所有写/查操作都天然支持批量——哪怕你只加一条，也要写成 ids=["id1"] 这种列表形式。

一个 Collection 里可以存无数条记录，每条记录由 id 唯一标识。同一个 Collection 内的所有记录必须使用相同维度的 embedding
当你调用 add(ids=["a","b"], documents=["x","y"]) 后，Chroma 内部会生成两条独立的记录，逻辑上等价于：
记录1: {id: "a", document: "x", metadata: None, embedding: [...]}
记录2: {id: "b", document: "y", metadata: None, embedding: [...]}

### 情景记忆的数据结构

| ----------- | -------- | --------------------------------------------------------------------- |
| `id`        | 字符串   | 稳定的 64 位 episode 哈希，作为 Chroma 记录 ID                        |
| `document`  | 字符串   | 脱敏后的本次压缩段摘要正文                                            |
| `metadata`  | 扁平字典 | 用户/会话哈希、起止轮次哈希、轮数、末轮时间、正文哈希、embedding 标识 |
| `embedding` | 浮点数组 | 摘要向量，用于相似度检索；维度由所选模型决定                          |

| 内容                        | 是什么                               | 输入 → 输出                                                      | 给谁用                               |
| --------------------------- | ------------------------------------ | ---------------------------------------------------------------- | ------------------------------------ |
| `UserProfile`、`Entities`   | Pydantic 数据结构，规定画像长什么样  | 偏好、商品类别、问题类别 → 合法画像对象                          | 抽取、合并、保存和读取都使用这个结构 |
| `ProfileRecord`             | 保存格式的数据结构                   | 画像对象、来源 episode ID → 可序列化记录                         | 保存到 Chroma，来源 ID 帮助失败重试  |
| `parse_profile(raw)`        | JSON 解析与校验函数                  | LLM 返回的字符串 → 合法画像增量；不合法则抛错                    | 画像抽取之后调用                     |
| `sanitize_profile(profile)` | 清洗函数，不调用模型和数据库         | 画像对象 → 去空白、规范化、去重、过滤已知敏感项的新对象          | 抽取结果校验后，以及合并、保存前使用 |
| `merge_profile(old, patch)` | 合并函数，不调用模型和数据库         | 旧画像、新增量 → 合并后的画像对象                                | 更新流程拿到两份数据后调用           |
| `ProfileUpdater`            | 把模型调用和数据库读写串起来的工具类 | store、Chroma collection、异步 LLM 抽取函数 → 可用的画像更新工具 | 应用启动层创建，长期记忆维护流程调用 |

另外修改了三个已有模块：

- `core/llm.py`：新增 `LLMClient.extract_profile(prompt)`，输入提示词，返回模型生成的 JSON 文本。使用现有模型/API 配置和独立的画像提取指令，拒绝被输出长度上限截断的结果。
- `memory/longterm.py`：episode 写 Chroma 成功后，登记画像待办；如果注入了 `ProfileUpdater`，继续尝试处理画像待办。
- `memory/store.py`：负责 Redis 待办交接、用户级锁、处理回执，不生成画像内容。

**上游**是“已经成功保存的 episode”；**下游**一方面是 Chroma 中的用户档案，另一方面是未来组装回答上下文的代码。未来回答前可读取画像作为背景，但当前 `ContextBuilder` 和 `/chat` 还不会自动读取它。

### 2. 什么时候调用，拿哪部分数据生成画像

不是每收到一句话就更新画像，也不是扫描全部聊天记录。按现有压缩流程，假设 Redis 已有 T1～T6 六轮，并已达到默认 10,800-token 阈值：

```text
T1、T2、T3、T4：本次要压缩的旧轮次
    → 摘要 LLM 生成 new_summary
    → 脱敏后形成 episode.summary
    → episode 成功写入 Chroma
    → 才允许登记和执行画像更新

T5、T6：最近两轮，也就是最近四条消息
    → 不参与本次摘要、episode 或画像提取
```

画像 LLM 真正收到的内容是 **`episode.summary` 这一段本次新增的脱敏摘要**，再加上画像提取指令。episode 的用户哈希、会话哈希、来源编号用来定位和管理记录，不作为画像正文发给模型。

episode 形成还受已有最少轮次规则限制：默认本次被压缩的旧轮次至少两轮。没有形成 episode、摘要失败、Redis 压缩提交冲突或 episode 写 Chroma 失败时，都不会登记本次画像更新。只压缩了一轮而未形成 episode，也不更新画像。

### 3. 画像是 LLM 生成的吗？与之前的 summary 调用有什么区别

**是，新增画像内容由 LLM 从本次 episode 摘要提取。** `ProfileUpdater.extract_profile(episode)` 会构造提示词，调用注入的 `llm.extract_profile`，正常一次抽取调用一次 LLM，默认抽取超时 15 秒；失败重试可能再次调用。

例如 episode 摘要是：“用户明确偏好宽松版型，咨询了运动鞋退换货。”希望模型输出：

```json
{
  "preferences": ["偏好宽松版型"],
  "entities": {
    "products": ["运动鞋"],
    "issue_types": ["退换货"]
  }
}
```

`preferences` 是明确的长期偏好；`products`、`issue_types` 是关注过的商品和问题类别。咨询过运动鞋不等于喜欢运动鞋。提示词要求不把 assistant 的建议当用户偏好、不猜测身份，但它仍然依赖摘要及模型提取的准确性。

模型返回后，代码解析完整 JSON，使用 Pydantic 检查字段和类型，再清洗内容。每个列表最多 10 项，每项最多 80 字符；额外字段、重复 JSON 字段、错误类型、超限响应都会被拒绝，不会直接把模型原文覆盖到数据库。

三个阶段不要混淆：

| 阶段               | 谁执行                                 | 输入 → 输出                                                   |
| ------------------ | -------------------------------------- | ------------------------------------------------------------- |
| 旧对话生成本次摘要 | 摘要 LLM，已有功能                     | T1～T4 原文 → new_summary                                     |
| 新旧会话摘要合并   | 摘要 LLM，已有功能；有旧摘要时才调用   | old_summary + new_summary → Redis 累计 summary                |
| 提取画像增量       | 画像 LLM，本次新增                     | 脱敏后的 new_summary，也就是 episode.summary → 画像 JSON 增量 |
| 新旧用户画像合并   | **Python `merge_profile()`，本次新增** | Chroma 旧画像 + 合法增量 → 新画像                             |

因此，本次新增的是画像提取这一处模型调用，**没有新增“让 LLM 合并用户画像”的调用**，也不是让 bge-m3 来生成画像。

### 4. 旧画像和新增画像怎么合并：由代码按规则处理

LLM 只交出本次的“增量”，不会拿旧画像生成一份完整替代品。`update_from_episode()` 在拿到合法增量后，获取用户级锁，从 Chroma 读取该用户最新画像，再调用 `merge_profile(old, patch)`。

例如只看 `preferences` 字段：

```text
旧画像：  ["优先考虑性价比", "偏好宽松版型"]
本次增量：["偏好宽松版型", "偏好棉质"]
合并结果：["偏好宽松版型", "偏好棉质", "优先考虑性价比"]
```

代码做法就是：**先放本次增量，再放旧条目，规范化后精确去重，最后保留前 10 项。** `products`、`issue_types` 各自按同样规则处理。

- 本次再次出现的条目排在前面，重复内容只留一份；去首尾空白、做字符规范化、忽略英文大小写后比较。
- 旧画像中本次没提到的内容继续保留，容量满时排在后面的旧条目会被挤掉。
- 增量为空不代表删除旧画像；把同一个增量直接重复合并，结果不变。
- 这里的“新信息优先”指本次处理的增量优先，不是对所有待办按事件时间进行全局排序。
- 没有实现同义词理解或语义冲突裁决。例如“偏好宽松”和“喜欢宽松衣服”可能同时保留；“喜欢红色”和“不喜欢红色”也不会自动由代码判断哪个应删除。

### 5. 最终保存到哪里，为什么还需要 Redis 和锁

**最终画像现在存在 Chroma 的 `user_profiles_v2_<模型哈希>` collection。** 本次已将原先 v1 的占位向量升级为真实语义向量，完整说明见下方第六件事。 每个用户一条记录，ID 是 `profile:<用户SHA-256>`，所以同一用户的不同 session 更新同一份档案。document 的形状如下，其中来源 ID 为示意值：

```json
{
  "profile": {
    "preferences": ["偏好宽松版型"],
    "entities": {
      "products": ["运动鞋"],
      "issue_types": ["退换货"]
    }
  },
  "last_episode_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "semantic_text": "长期偏好：偏好宽松版型\n关注商品类别：运动鞋\n咨询问题类别：退换货"
}
```

metadata 保存用户哈希、来源 episode ID、来源时间、更新时间及 embedding 模型标识。document 现在还保存 `semantic_text`；它由清洗后的完整画像确定性拼接，经配置的 embedding 模型得到真实向量。`get_profile()` 仍按 ID 精确读取，不调用 embedding；新增的相似度检索才把问题或画像文本编码查询。旧的一维 `user_profiles_v1` 保留作为显式迁移来源，不与新向量混写。

Redis 不保存第二份完整画像，保存的是任务与回执：

- `memory:pending_profiles:v1`：待办 Hash，episode ID → 脱敏 Episode JSON。失败后还知道“该从哪段摘要重新提取”。
- `memory:applied_profiles:v1`：完成回执 Hash，episode ID → `1`。重复交接已完成任务时跳过，不再重复提取。

episode 写 Chroma 成功后，Redis 用同一事务“移除 episode 待办 + 登记画像待办”。画像保存成功后，再用同一 Redis 事务“记录完成回执 + 移除画像待办”。这些 Hash 无 TTL，回执随任务数量增长，清理留给后续数据保留功能。

用户级本地锁和 Redis 租约保护“读最新画像 → 合并 → 写回”，防止同一用户两个 session 各读到旧档案再互相覆盖。慢 LLM 提取在锁外。Chroma 写成功而 Redis 确认失败时，利用画像里的 `last_episode_id` 补回执；覆盖下一份画像前也先补上一份回执。它是失败可重试的交接，不是跨库事务。

敏感信息在抽取前脱敏，候选画像在合并保存前再次过滤；含已知手机号、邮箱、身份证或相关占位符的条目整项丢弃，并限制身份字段和已知敏感标签。日志只记异常类型。这不保证识别所有隐式姓名、地址或混淆 PII；本次也不改变原始聊天和会话 summary 的保存策略。

### 6. 代码怎么使用，当前哪些已经接好

`ProfileUpdater` 负责更新流程，`LLMClient.extract_profile` 负责实际请求模型。初始化时把模型方法传进去，这叫“注入”：画像模块不自己选另一个模型或创建第二套 Key。

```python
from memory.profile import ProfileUpdater
from memory.longterm import LongTermMemory
from memory.compactor import MemoryCompactor

# 应用启动层：先加载环境配置，并准备已有的 store 和 llm。
profiles = ProfileUpdater.from_env(store, llm.extract_profile)
longterm = LongTermMemory.from_env(profile_updater=profiles)
compactor = MemoryCompactor(store, llm.summarize, longterm=longterm)

# 一轮成功问答已经提交 Redis 后，由调用方启动后台维护。
compactor.start(user_id, session_id)

# 将来组装回答上下文时读取画像，拿到 UserProfile 对象。
profile = await profiles.get_profile(user_id)
profile_data = profile.model_dump()  # 转成普通字典，供上下文组装代码使用。

# 失败待办可单独重试，不要求再压缩一次历史或再产生新 episode。
completed = await profiles.flush_pending()
```

| `ProfileUpdater` 方法          | 何时调用                            | 返回什么                                                                                                |
| ------------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `from_env(store, extract)`     | 启动时初始化                        | 一个画像工具对象，不立即提取画像                                                                        |
| `extract_profile(episode)`     | 更新流程内部，需要本次增量时        | 合法的 `UserProfile` 增量，自己不写库                                                                   |
| `update_from_episode(episode)` | 处理一条已登记的待办时              | `updated` 更新、`unchanged` 内容不变、`already_applied` 已处理、`not_pending` 无匹配待办、`failed` 失败 |
| `flush_pending(limit=20)`      | episode 写入后，或维护器/人工重试时 | 本批完成的任务数                                                                                        |
| `get_profile(user_id)`         | 未来回答前需要用户背景时            | 用户画像对象；没有记录返回空画像，读取坏数据或连接失败抛错                                              |

**已经接好的入口**是 `LongTermMemory.flush_pending(store)`：它成功保存 episode 后登记画像待办，并在注入 updater 时继续调用 `profiles.flush_pending()`；即使没有新 episode，也能尝试已有画像待办。没有注入 updater 时，只登记画像任务，不自动请求 LLM。

**还没接好的应用行为**是 `/chat` 自动提交并启动整条维护链路，以及回答前自动读取画像放进上下文。以上是调用方接入示例，不表示当前聊天接口已经执行这些操作。画像失败保留旧值和待办，不回滚已成功的 episode；现有 compactor 对整个长期记忆 flush 的 15 秒等待上限可能取消画像抽取，此时待办保留，可独立重试。

## 今天第六件事：用户画像改为真实向量，增加相似度检索

### 这次改了什么，为什么

之前画像的 embedding 固定为 `[1.0]`，只能靠用户 ID 找档案，不能表示画像内容的相似程度。现在把**合并完成、清洗后的完整画像**编码成真实向量，同时保留结构化 JSON，支持相似度查询。上游仍是 episode 后的画像更新，下游是 Chroma 写入、当前用户记忆召回，以及显式的相似用户分析接口。

**本次不改变画像提取的材料和合并方式：仍从 episode.summary 调用 LLM 提取增量，再由 Python 合并旧画像。** 新增的是合并之后的 embedding 与查询能力，不是增加一次 LLM 合并，也没有改成从裁剪后的 working memory 提取。

### 到底把什么向量化

新增纯函数 `profile_to_embedding_text(profile)`：输入合法的完整画像，输出例如下面的文字。

```text
长期偏好：偏好宽松版型；偏好棉质
关注商品类别：运动鞋
咨询问题类别：退换货
```

三个列表各自按固定顺序排序后拼接，避免条目仅仅换顺序就改变向量输入。**用户 ID/哈希、session、来源 episode ID、时间戳、处理回执都不参与向量化。** 敏感候选已先过滤，空画像不生成向量、不创建 Chroma 记录。

向量化的是“能说明用户偏好和关注内容的文字”，不是把哈希当特征，也不是对包含各种运维字段的整个 JSON 编码。这里表示的是综合画像，包含咨询类别，不等价于经过验证的纯“审美品味”。

### 谁负责生成，何时调用

```text
LLM 根据 episode 摘要生成画像增量
    → 校验、过滤敏感项
    → 用户级锁内读取最新旧画像
    → Python merge_profile() 合并
    → profile_to_embedding_text() 拼出完整画像语义文本
    → embedding 模型把文本变成浮点数组
    → 同一次 Chroma upsert 保存 JSON、metadata、真实向量
    → Redis 确认画像待办
```

embedding 和 LLM 是不同能力。`memory/embeddings.py` 从原来的 `longterm.py` 提取共用配置与向量校验，episode 和画像都使用它：

- `COMMERCEMIND_MEMORY_EMBEDDING_PROVIDER=default`：用本地默认模型，不产生 embedding API 费；首次使用需下载模型。
- `siliconflow`：使用配置的远程 API，默认模型名 `BAAI/bge-m3`；写入画像和向量查询可能产生服务费用。
- `auto`：有 `SILICONFLOW_API_KEY` 走远程，没有走本地默认模型；失败时不静默换模型。

本次没有修改真实 `.env`、没有自动下载模型，也没有请求真实付费 API。本地 bge-m3 后端仍未实现；模型输入长度限制取决于所选后端。embedding 失败或返回空、全零、NaN 等非法向量时，不覆盖旧记录，画像待办保留。

### 新增/修改文件及能力的输入输出

| 文件 / 能力 | 输入 → 输出 | 上下游与调用时机 |
| --- | --- | --- |
| `memory/embeddings.py`：`embedding_from_env()` | 环境变量 → embedding 标识、编码 callable | 启动创建 episode/画像工具时共用；只选择后端，不主动编码文本 |
| `encode_vectors(embed, texts)` | 编码函数、文本列表 → 校验后的浮点向量列表 | 保存或查询时调用；非法数量、维度、数值拒绝 |
| `memory/longterm.py` | 原有 episode 写入/查询参数 → 原有结果 | 改用共用 helper，保留原 collection 命名、配置及行为 |
| `profile_to_embedding_text(profile)` | 完整清洗画像 → 固定格式语义文本 | 保存前、以画像查相似用户前使用，不调用 LLM |
| `ProfileMatch` | 用户哈希、合法画像、cosine 分数 | 相似度查询的结果数据结构，不含原始用户 ID |
| `ProfileUpdater.search(user_id, query)` | 用户 ID、当前问题、可选最低分 → 最多一条 ProfileMatch | 问题脱敏编码，只查当前用户；用于个人记忆召回 |
| `find_similar_users(user_id, top_k=3, min_score=.55)` | 当前用户 ID → 其他用户的 ProfileMatch 列表 | 读取该用户画像作为查询文本，显式跨用户分析，排除自己 |
| `get_profile(user_id)` | 用户 ID → 完整画像 | 仍按 ID 精确取，读取不需要 embedding；适合全量加载个人背景 |
| `reindex_user(user_id)` | 用户 ID → 是否完成迁移 | 读取显式指定的旧 collection，清洗并重建真实向量，不调用 LLM、不删除旧档案、不覆盖已有新记录 |
| `.env.example` | 新增可选迁移来源 collection 配置 | 默认旧 `user_profiles_v1`；切模型时可指定上一模型的 collection |
| `tests/test_memory_profile.py`、`docs/profiles.md` | fake / 可选真实 Chroma 测试及使用示例 | 验证语义文本、向量、过滤、模型隔离、失败保留和迁移 |

### 在 Chroma 中怎么存，旧数据怎么办

新 collection 名是 `user_profiles_v2_` 加 embedding ID 的 SHA-256 前 12 位。collection metadata 记录 `profile_schema=v2`、`embedding_id`、`hnsw:space=cosine`，不同模型分开，初始化时检查是否匹配。每个用户在当前模型下仍只有一条 `profile:<用户SHA-256>` 记录，JSON 和向量一起更新，不额外建第二条画像。

- document：完整 `profile` JSON、`last_episode_id` 和实际用于编码的 `semantic_text`。
- metadata：用户哈希、来源 episode、来源时间、更新时间及 `embedding_id`。
- embedding：`semantic_text` 经模型生成的完整浮点数组，长度由模型决定。

旧 `user_profiles_v1` 的一维数据保留，不直接混写新向量。`get_profile()` 优先读当前模型 collection，缺失时可精确读取配置的旧来源；向量查询只读当前新 collection。已处理的 episode 回执不会因换模型失效，所以需要显式迁移，不能靠重放旧任务来重建向量：

```python
# 默认从旧 user_profiles_v1 迁移指定用户；不会调用画像提取 LLM。
migrated = await profiles.reindex_user(user_id)
```

新 collection 已有该用户则跳过，避免旧数据覆盖新数据。切换 embedding 模型时，可配置 `COMMERCEMIND_MEMORY_PROFILE_SOURCE_COLLECTION` 为上一个模型的 collection，再迁移需要的用户；没有迁移的用户暂不会出现在新模型的向量结果里。本次不自动批量迁移真实用户。

### 怎么取，怎么给 context 用

```python
# 初始化方式不变；embedding 配置由 from_env 内部读取。
profiles = ProfileUpdater.from_env(store, llm.extract_profile)

# 方式1：直接拿当前用户的整份画像，不调用 embedding。
profile = await profiles.get_profile(user_id)

# 方式2：根据当前问题召回自己的画像，默认分数 >= 0.55。
hits = await profiles.search(user_id, "推荐适合我的运动鞋")
profile_data = [hit.profile.model_dump() for hit in hits]

# 方式3：可信后台显式查相似用户，不作为当前用户自己的记忆。
peers = await profiles.find_similar_users(user_id, top_k=3)
```

分数为 `1 - cosine_distance`，不是正确率。个人召回同时在数据库和返回结果中检查用户一致；跨用户查询排除自己，两者都检查模型、去重并过滤最低分。查询失败返回空列表，参数非法则报错。

### 新增什么、上下游是谁、什么时候调用

上游是“成功问答已存入 Redis”的聊天调用方；它调用 `maintenance.submit(user_id, session_id)`，立即得到状态，不等摘要完成。下游分两条：

```text
成功一轮问答 → Redis commit_turn
    → submit(user_id, session_id)
    → 有界会话队列 → 固定 worker
    → compactor 重新读全部 working memory、判断 token 阈值
    → LLM 摘要/必要时合并摘要 → WATCH/MULTI 条件提交裁剪

独立的定时扫描器（没有新聊天也运行）
    → Redis episode 待写项 → embedding/Chroma 重试
    → 画像待办 → 抽取、合并和保存重试
```

队列只存用户/会话标识，不存第二份聊天正文。摘要输入仍是快照最近两轮之前的消息，最近四条不摘要、不裁剪；画像仍按现有 episode.summary 抽取，本步没有调整数据来源。

| --- | --- | --- |

### 队列怎么有界，同会话怎么合并

默认 `max_pending=128`，限制**排队中 + 运行中的不同会话总数**；默认 2 个 worker。每个会话最多一份排队/运行状态，不再为每个会话创建 Task。传入 longterm 时另有一个待写扫描 Task，因此压缩并发与扫描并发分别有界，限制作用于单个 maintainer 实例。

- `queued`：新会话加入队列。
- `coalesced`：同会话已经在队列中，或正在处理；没有复制任务。
- 正在处理时又收到请求：记一个 dirty 标记，处理完后重新排到队尾检查一次。50 次重复触发也只多一次待检查；运行中又有新消息则可继续标记下一次。
- `full`：不同会话数满了，本次维护跳过，问答仍在 Redis，不阻塞回答也不删除数据。同一已存在会话即使容量满也可以合并。由于容量包含运行中会话，dirty 后续检查有预留位置。
- `stopped`：未启动、退出中或已关闭，不接收请求。

该会话再次检查时重新读最新快照，不使用上次摘要前的旧消息列表。dirty 项排到队尾，其他已排队会话可以先处理。

### 失败重试、WATCH/MULTI 和待写重试分别干什么

**压缩任务重试**：`failed`、`conflict` 或普通异常，默认最多重试 2 次，即首次加重试共 3 次。退避从 0.25 秒起翻倍，上限 5 秒。每次重新调用 compact、重新读取快照；成功、低于阈值或只剩最近两轮时结束。耗尽次数清理本次内存任务，旧历史保留，后续新 submit 可再触发；不无限重试。退避占 worker，但不占会话提交锁。

**Redis 提交保护**：复用 `store.commit_compaction()` 的 WATCH/MULTI。生成期间可以追加新轮次；提交时保留快照最近两轮及所有新增轮次。两个任务若针对同一旧状态生成摘要，只允许符合条件的提交成功，另一个返回 conflict，再按新快照重试。跨进程仍可能重复调用 LLM，本步不承诺全局只生成一次摘要，但不会用过时摘要重复覆盖已变更的数据。

**episode/画像待写重试**：扫描器启动时立即尝试一次，每次结束后默认等 5 秒；默认每批 20 项，单次等待预算 30 秒。复用 `longterm.flush_pending(store)`，成功才确认 Redis 待办。即使没有新会话或没有达到压缩阈值也会处理；注入 profile_updater 时会继续画像待办。Chroma 失败不导致已经成功的摘要再次生成；画像抽取本身失败后重试仍可能调用画像 LLM。

扫描异常/超时只记录异常类型，下一周期继续；扫描器与压缩队列独立，Chroma 故障不占用会话队列名额。多进程可能重复投递待办，继续使用已有稳定 episode ID/upsert、画像用户锁及处理回执保证重试安全。

### 怎么接入，当前接到哪里

```python
from memory.maintainer import MemoryMaintainer

# 应用启动，复用已经创建好的 compactor、store、longterm。
maintenance = MemoryMaintainer.from_env(compactor, store=store, longterm=longterm)
maintenance.start()

# 每次成功的一轮问答已经通过 store.commit_turn(...) 落库后：
status = maintenance.submit(user_id, session_id)
# 这里不 await 摘要；full 只表示这次维护没排进去，聊天回答仍正常返回。

# 应用退出：先停维护，之后再关闭依赖。
await maintenance.close(drain=True, timeout_s=5)
```

不能同时在此链路再调用旧 `compactor.start()`，否则会绕过统一队列的容量/worker 限制。没有传 longterm 就不启动自动 episode/画像待写扫描；画像 updater 没有注入则画像待办保留但不执行。

关闭时先停止接收，可限时排空，超时则取消任务。未提交的压缩取消后保留原历史，已经原子提交的不回滚；Redis 待写项不会因为关机清空。timeout_s 只限制排空等待，遇到已启动的画像写线程仍等待安全收尾，不强制杀线程。调用方仍负责关闭 Redis、LLM 等依赖。
