| `api/main.py` | 创建 FastAPI 应用，提供 `/health` 和 `/chat` |
| `tests/test_chat_api.py` | 12 个 mock 测试，不依赖真实 Key 和网络 |

| `pytest.ini` | 补充 pytest-asyncio 的 fixture loop scope 配置 |

当前仍未 commit，且没有引入 Redis、ChromaDB、意图识别、Agent、RAG、MCP 和监控。

### 接口 1：`GET /health`

传入参数：无。

返回值：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | `ok` 或 `degraded` |
| `model_configured` | boolean | 是否配置了有效格式的模型 Key |
| `model` | string | 当前模型 ID |
| `detail` | string/null | 未配置 Key 时给出提示 |

内部逻辑：

1. 读取应用启动时加载的 `Settings`；
2. 判断 `ANTHROPIC_API_KEY` 是否为空，或是否仍是 `xxx` 这类模板占位符；
3. 不调用模型，也不验证 Key 是否真实有效，只判断“有没有配”；
4. 返回 `ok` 或 `degraded`。

### 接口 2：`POST /chat`

传入参数（JSON Body）：

```json
{
  "message": "退款一般多久到账？"
}
```

| 字段 | 类型 | 约束 |
|---|---|---|
| `message` | string | 必填，1-12000 字符；会去掉首尾空格，空字符串或全空格返回 422 |

成功返回值：

```json
{
  "request_id": "5f2c1a3b4d5e",
  "response": "退款一般 3-5 个工作日到账。",
  "latency_ms": 1234.5
}
```

失败返回值：

```json
{
  "detail": "模型响应超时，请稍后重试",
  "request_id": "5f2c1a3b4d5e",
  "error_code": "llm_timeout"
}
```

内部逻辑：

1. Pydantic 校验 `message`，空消息直接返回 422；
2. 生成 `request_id`，记录开始时间；
3. 检查应用是否已配置 LLM，未配置返回 503；
4. `LLMClient.chat()` 调用 `AsyncAnthropic.messages.create()`，带上 system prompt、模型、`max_tokens` 和超时；
5. 从响应 content 中提取文本；
6. 把 Anthropic SDK 异常转换成统一的 `LLMError`，再由接口返回对应状态码；
7. 日志只记录 `request_id`、消息长度、耗时和错误类型，不记录 Key 和用户原文；
8. 成功时返回文本、耗时和 `request_id`，并写入 `X-Request-ID` 响应头。

常见错误：

| 场景 | 状态码 | `error_code` |
|---|---|---|
| 消息为空或全空格 | 422 | FastAPI 默认校验错误 |
| 未配置 Key | 503 | `model_not_configured` |
| 模型超时 | 503 | `llm_timeout` |
| Key / Base URL 鉴权失败 | 502 | `llm_auth_failed` |
| 模型 ID 或接口地址不存在 | 502 | `llm_not_found` |
| 模型请求参数错误 | 502 | `llm_bad_request` |
| 模型返回空内容 | 502 | `llm_empty_response` |
| 未预期异常 | 500 | `internal_error` |

### Swagger 是怎么配置出来的

不需要手写 Swagger 配置，FastAPI 会自动生成：

1. `FastAPI(...)` 构造时设置 `docs_url="/docs"`，就会挂载 Swagger UI 页面；
2. FastAPI 根据路由装饰器（`@app.get`、`@app.post`）自动收集路径、方法和说明；
3. Pydantic 模型（`ChatRequest`、`ChatResponse`、`HealthResponse`）自动生成请求/响应 JSON Schema；
4. `Field(min_length=1, max_length=12000)`、`response_model` 和 `tags` 会体现在 Swagger 文档里；
5. 浏览器打开 `/docs` 时，Swagger UI 读取 FastAPI 自动生成的 `/openapi.json`，渲染成可交互页面。

所以 Swagger 的本质是：**FastAPI 生成 OpenAPI 描述文件，Swagger UI 读取并展示它**。

### 一、Docker 是什么

可以先用做饭类比：

| 概念 | 类比 |
|---|---|
| `Dockerfile` | 菜谱，写清楚需要什么原料、按什么步骤做 |
| 镜像（image） | 按菜谱做好的“半成品模板”，只读，可以复制很多份 |
| 容器（container） | 拿半成品真正开火运行起来的一份菜，可以启动、停止、删除 |
| `docker-compose.yml` | 点菜清单，告诉 Docker 要启动哪些容器、端口怎么开、环境变量怎么传 |
| 镜像仓库（registry） | 存放镜像的“应用商店”，例如 Docker Hub |

Docker 不是虚拟机。虚拟机要模拟一整套硬件和操作系统；Linux 上容器直接共享宿主机的 Linux 内核，只隔离进程、文件系统、网络等资源，所以更轻、更快。macOS 上 Docker Desktop 会先启动一个轻量 Linux 虚拟机，容器共享的是这个虚拟机里的内核。

容器里的应用看到的是一套独立环境：

- 独立文件系统；
- 独立网络和 IP；
- 独立进程空间；
- 通过端口映射把容器端口暴露给宿主机。

### 二、Docker 能做什么，不能做什么

能做到：

- **环境一致**：本机能跑，换一台机器也能用同一个镜像跑，不依赖本机 Python 版本和全局包；
- **依赖隔离**：容器里的 Python、依赖包和应用不会和宿主机其他项目冲突；
- **一键启动**：`docker compose up -d` 完成创建容器、注入环境变量、启动服务；
- **可复制**：镜像可以给别人，也可以部署到服务器；
- **进程隔离**：应用崩溃或异常不会直接污染宿主机环境；
- **健康检查和自动重启**：容器定期访问 `/health`，失败会标记 unhealthy；进程退出后按策略重启；
- **方便回滚**：保留旧镜像，就可以快速切回旧版本。

不能做到：

- **不能替代配置**：`ANTHROPIC_API_KEY`、模型 ID 仍然要放在 `.env` 里；
- **不能解决网络问题**：访问不到模型接口，容器里也一样访问不到；
- **不会自动热更新**：代码是构建时复制进镜像的，改代码后必须重新构建镜像；
- **当前没有数据持久化**：没有挂载 volume，删除容器后容器内新产生的数据会丢失；
- **不是虚拟机**：容器共享宿主机内核，不能在里面运行一个完全不同的操作系统内核。

### 三、输入命令后 Docker 会干什么

最常用的一条：

```bash
docker compose up -d --build
```

执行过程：

1. `docker compose` 读取当前目录的 `docker-compose.yml`；
2. 解析 `${PIP_INDEX_URL:-https://pypi.org/simple}`，先看 shell 环境变量，再看 `.env`；
3. 读取 `env_file: .env`，准备在容器启动时把这些变量注入进去；
4. 把 `build.context` 指定的当前目录（构建上下文）发给 Docker 守护进程；
5. Docker 按 `Dockerfile` 逐行执行：
   - 拉取 `python:3.12-slim` 基础镜像；
   - 设置工作目录和环境变量；
   - 复制 `requirements.txt`；
   - 执行 `pip install` 安装依赖；
   - 创建非 root 用户；
   - 复制 `api/` 和 `core/` 代码；
6. 构建完成后打上标签 `commercemind:local`，得到镜像；
7. 用这个镜像创建容器 `commercemind-app`；
8. 把宿主机的 `127.0.0.1:8000` 映射到容器内的 `8000`；
9. 把 `.env` 里的变量注入容器；
10. 在容器内执行 `python -m uvicorn api.main:app --host 0.0.0.0 --port 8000`；
11. `-d` 表示后台运行，命令执行完会回到终端；
12. 之后每隔 30 秒执行一次健康检查，成功则状态变成 `healthy`。

常用命令：

| 命令 | Docker 做什么 |
|---|---|
| `docker compose build` | 只构建镜像，不启动容器 |
| `docker compose up -d` | 用已有镜像创建并后台启动容器；镜像不存在时会尝试构建 |
| `docker compose up -d --build` | 先重新构建镜像，再启动容器；适合代码改动后 |
| `docker compose ps` | 查看容器状态、端口和健康状态 |
| `docker compose logs -f commercemind` | 持续查看容器标准输出日志，相当于 `tail -f` |
| `docker compose stop` | 停止容器，但保留容器 |
| `docker compose start` | 启动已停止的容器 |
| `docker compose down` | 停止并删除容器和默认网络，但保留镜像 |
| `docker compose down -v` | 连同数据卷一起删除；当前没有数据卷，所以和 `down` 差别不大 |
| `docker compose up -d --force-recreate commercemind` | 强制重新创建容器；适合改了 `.env` 后 |

### 四、专有名词解释

读下面的配置前，先记住：命令行里的 `-d` 是 detached（分离）模式，表示让容器在后台运行；`--build` 表示先按 Dockerfile 构建镜像；`-f` 是 follow（跟随）模式，会持续输出新日志；`-v` 在 `down -v` 中表示同时删除数据卷。

| 名词 | 解释 |
|---|---|
| Docker Engine / 守护进程 | 后台真正负责拉镜像、构建、运行容器的服务 |
| Docker CLI | 我们在终端输入的 `docker`、`docker compose` 命令 |
| Docker Desktop | macOS 上的桌面程序，内部包含一个 Linux 虚拟机、Docker Engine 和 CLI |
| 镜像 image | 只读模板，包含应用代码、Python 解释器和依赖包 |
| 容器 container | 镜像运行起来的实例，有自己的进程、网络和可写层 |
| Dockerfile | 构建镜像的步骤文件 |
| 构建 build | 按 Dockerfile 把基础镜像 + 依赖 + 代码打包成新镜像 |
| 构建上下文 context | `docker build` 时发给守护进程的目录，默认是 `.` |
| 基础镜像 base image | 新镜像的起点，这里是 `python:3.12-slim` |
| 层 layer | Dockerfile 中每条指令通常生成一层；层可以复用缓存 |
| 缓存 cache | 前面的层没变时，Docker 不重复执行，构建会更快 |
| 标签 tag | 镜像版本名，例如 `commercemind:local` 中的 `local` |
| 仓库 registry | 存放镜像的服务，例如 Docker Hub |
| Docker Compose | 用 YAML 描述和启动容器的工具 |
| 服务 service | `docker-compose.yml` 中的一个容器定义，这里是 `commercemind` |
| 端口映射 | `宿主机端口:容器端口`，让外部能访问容器内服务 |
| 环境变量 | 运行时可变的配置，例如 API Key、模型 ID |
| `env_file` | 把文件里的键值对注入容器环境变量 |
| `ARG` | 只在构建阶段使用的变量 |
| `ENV` | 写进镜像、构建和运行时都能读取的环境变量 |
| `WORKDIR` | 容器内的工作目录 |
| `COPY` | 构建时把宿主机文件复制进镜像 |
| `RUN` | 构建时在镜像内执行命令 |
| `CMD` | 容器启动时默认执行的命令 |
| `EXPOSE` | 声明容器准备使用哪个端口，只是文档说明，不等于发布端口 |
| `USER` | 指定容器运行时使用哪个用户 |
| `HEALTHCHECK` | 定期检查容器内服务是否健康 |
| 数据卷 volume | 独立于容器生命周期的持久化存储；当前没有使用 |
| 网络 network | Docker 创建的虚拟网络；当前只有一个服务，使用默认网络 |
| 命名空间 namespace | 隔离进程、网络、文件系统等资源 |
| cgroup | 限制容器可用的 CPU、内存等资源 |
| 多阶段构建 | 一个 Dockerfile 里定义多个 `FROM` 阶段，这里分为 `base` 和 `production` |
| `.dockerignore` | 构建时排除某些文件，避免把 `.venv`、`.git` 等发给守护进程；当前还没加 |

### 五、`Dockerfile` 逐行解释

```dockerfile
FROM python:3.12-slim AS base
WORKDIR /app
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    PYTHONPATH=/app
ARG PIP_INDEX_URL=https://pypi.org/simple
ENV PIP_INDEX_URL=${PIP_INDEX_URL}
COPY requirements.txt .
RUN pip install --upgrade pip && \
    pip install -r requirements.txt
FROM base AS production
RUN useradd --create-home --uid 1000 commercemind
COPY --chown=commercemind:commercemind api ./api
COPY --chown=commercemind:commercemind core ./core
USER commercemind
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3).read()"
CMD ["python", "-m", "uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

| 配置 | 含义 |
|---|---|
| `FROM python:3.12-slim AS base` | 以官方 Python 3.12 精简版为基础镜像，并把这一阶段命名为 `base` |
| `WORKDIR /app` | 后续命令都在容器内 `/app` 目录执行，目录不存在会自动创建 |
| `PYTHONUNBUFFERED=1` | Python 输出不缓冲，日志能立刻出现在 `docker compose logs` |
| `PYTHONDONTWRITEBYTECODE=1` | 不生成 `__pycache__`，减少镜像里的无用文件 |
| `PIP_NO_CACHE_DIR=1` | pip 不保存下载缓存，减小镜像体积 |
| `PIP_DISABLE_PIP_VERSION_CHECK=1` | 关闭 pip 版本检查，减少构建输出和网络请求 |
| `PYTHONPATH=/app` | 让容器内能直接 `import api`、`import core` |
| `ARG PIP_INDEX_URL=...` | 构建参数，默认使用官方 PyPI；构建时可覆盖 |
| `ENV PIP_INDEX_URL=${PIP_INDEX_URL}` | 把构建参数变成环境变量，供后面的 `pip install` 使用 |
| `COPY requirements.txt .` | 只先复制依赖清单，不要一开始复制全部代码 |
| `RUN pip install ...` | 构建时安装依赖；依赖没变时会复用缓存层 |
| `FROM base AS production` | 基于 `base` 阶段创建最终运行阶段 `production` |
| `RUN useradd ...` | 创建 uid 1000 的非 root 用户，降低容器权限 |
| `COPY --chown=... api ./api` | 只复制运行需要的 `api/` 代码，并设置文件所有者 |
| `COPY --chown=... core ./core` | 只复制运行需要的 `core/` 代码 |
| `USER commercemind` | 容器启动后用非 root 用户运行，更安全 |
| `EXPOSE 8000` | 声明应用监听 8000；真正对外开放端口由 Compose 的 `ports` 决定 |
| `HEALTHCHECK ...` | 每 30 秒检查一次 `/health`，超时 5 秒；启动后的前 10 秒失败不计入重试，连续失败 3 次标记 unhealthy |
| `CMD [...]` | 容器启动命令；`0.0.0.0` 表示监听容器所有网卡，否则宿主机映射进不来 |

几个关键设计：

- **先复制 `requirements.txt` 再复制代码**：改业务代码时，`pip install` 这一层还能用缓存，构建更快；
- **只复制 `api/` 和 `core/`**：当前运行不需要 `tests/`、`docs/`、`.env`，镜像更小，也不会把本地文件带进去；
- **使用非 root 用户**：即使应用被攻破，容器内权限也更低；
- **健康检查用 Python 而不是 curl**：`python:3.12-slim` 没有预装 `curl`，用 Python 标准库最省事。

可以优化的地方：当前没有 `.dockerignore`，构建时仍会把 `.venv`、`.git` 等目录作为构建上下文发给 Docker。虽然它们不会被 `COPY` 进镜像，但会让构建变慢。

### 六、`docker-compose.yml` 逐行解释

```yaml
services:
  commercemind:
    build:
      context: .
      target: production
      args:
        PIP_INDEX_URL: ${PIP_INDEX_URL:-https://pypi.org/simple}
    image: commercemind:local
    container_name: commercemind-app
    ports:
      - "127.0.0.1:8000:8000"
    env_file:
      - path: .env
        required: false
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3).read()"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```

| 配置 | 含义 |
|---|---|
| `services:` | 声明要运行的服务列表 |
| `commercemind:` | 服务名，也是默认容器网络里的主机名 |
| `build.context: .` | 用当前目录作为构建上下文，Docker 从这里读取 Dockerfile 和复制文件 |
| `build.target: production` | 只构建 Dockerfile 中名为 `production` 的最终阶段 |
| `build.args.PIP_INDEX_URL` | 传给 Dockerfile 的构建参数；shell 没设置时用 `.env` 里的值，再没有就用官方 PyPI |
| `image: commercemind:local` | 构建出的镜像名和标签 |
| `container_name: commercemind-app` | 固定容器名，方便 `docker logs`、`docker exec`；不写会自动生成随机名字 |
| `ports: "127.0.0.1:8000:8000"` | 宿主机 `127.0.0.1:8000` 映射到容器 `8000`；只允许本机访问 |
| `env_file.path: .env` | 启动容器时把 `.env` 里的变量注入容器，不会打进镜像 |
| `env_file.required: false` | `.env` 不存在也允许启动；此时 `/health` 会提示未配置 Key |
| `restart: unless-stopped` | 容器异常退出或 Docker 重启后自动拉起；手动 `stop` 后不自动拉起 |
| `healthcheck` | Compose 层的健康检查，和 Dockerfile 里的 HEALTHCHECK 作用相同，这里会覆盖镜像里的设置 |
| `interval: 30s` | 每 30 秒检查一次 |
| `timeout: 5s` | 单次检查超过 5 秒算失败 |
| `retries: 3` | 连续失败 3 次后标记 unhealthy |
| `start_period: 10s` | 容器刚启动的 10 秒内失败不计入重试 |

几个关键设计：

- **`ports` 左边写 `127.0.0.1`**：只绑定本机回环地址，局域网其他机器访问不到，适合开发阶段；
- **`.env` 用 `env_file` 注入**：Key 不进入镜像，换环境只需要换 `.env`；
- **没有 `volumes`**：当前应用不写需要持久化的数据；以后加 Redis/Chroma 时再挂载数据卷；
- **没有 `depends_on`**：当前只有一个服务；以后加入 Redis/Chroma 后再配置启动顺序；
- **没有显式 `networks`**：Compose 会自动创建一个默认网络，当前一个容器够用。

### 七、怎么验证 Docker 启动成功

```bash
cd /Users/lixinyi/Desktop/commerceMind

# 1. 构建并后台启动
docker compose up -d --build

# 2. 看容器状态，期望 Up (healthy)
docker compose ps

# 3. 看启动日志，期望有 Uvicorn running on http://0.0.0.0:8000
docker compose logs --tail=50 commercemind

# 4. 健康检查
curl -s http://127.0.0.1:8000/health | python -m json.tool --no-ensure-ascii

# 5. 真实对话
curl -i -X POST http://127.0.0.1:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"message": "退款一般多久到账？"}'

# 6. 浏览器打开 Swagger
open http://127.0.0.1:8000/docs
```

判断成功：

- `docker compose ps` 显示 `Up (healthy)`；
- `/health` 返回 `200`，配置了真实 Key 时 `model_configured: true`；
- `/chat` 返回 `200`，有 `response` 和 `latency_ms`；
- `docker compose logs` 里能看到 `chat_start`、`chat_done` 和 `request_id`；
- 停止容器后重新 `docker compose up -d` 不需要重新构建，说明镜像已经固化。

改代码和改配置的区别：

| 改动 | 要执行的命令 |
|---|---|
| 改 `api/` 或 `core/` Python 代码 | `docker compose up -d --build commercemind` |
| 改 `.env` | `docker compose up -d --force-recreate commercemind` |
| 改 `requirements.txt` | `docker compose up -d --build commercemind` |
| 只改 `docker-compose.yml` 的端口 | `docker compose up -d` |

### 八、当前 Docker 配置的边界

- 只有 app 一个容器，没有 Redis、ChromaDB、Nginx、Prometheus；
- 没有数据卷，容器删除后不会保留容器内数据；
- 没有热更新，Python 代码是构建时复制进镜像的，改完必须重建；
- `.env` 不进入镜像，但 `docker compose config` 会把注入的环境变量打印出来，**里面包含 API Key，截图或分享前要打码**；
- 容器以非 root 用户运行；
- 端口只绑定 `127.0.0.1`，默认只有本机能访问。

### 九、常见问题

| 问题 | 原因和处理 |
|---|---|
| `port is already allocated` | 宿主机 8000 被占用；停掉占用进程，或改 Compose 左侧端口，例如 `127.0.0.1:8010:8000` |
| `pip install` 很慢或超时 | 用国内镜像构建：`PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple docker compose build` |
| 改了代码但容器没变化 | 代码在镜像里，需要 `docker compose up -d --build commercemind` |
| 改了 `.env` 但容器没变化 | 环境变量在创建容器时注入，需要 `docker compose up -d --force-recreate commercemind` |
| `docker compose ps` 显示 `unhealthy` | 看 `docker compose logs commercemind`，再确认 `/health` 是否返回 200 |
| 容器启动后马上退出 | 看日志；常见原因是启动命令报错或依赖缺失 |
| `docker compose down` 后镜像还在吗 | 在，`down` 只删容器和网络；要删镜像用 `docker image rm commercemind:local` |
| 为什么 `EXPOSE` 了还要写 `ports` | `EXPOSE` 只是声明，`ports` 才真正把端口映射到宿主机 |
