### 3. 行为说明

**默认关闭：** 直接构造 `ToolSettings()` 时 `enabled=False`，库调用方和测试不会因为导入配置就隐式启用工具；应用进程是否开启由 `.env` 经 `Settings.from_env()` 决定。

### 6. 工具管理器机制说明（T1–T11 目标实现，尚未落地）

> 当前只完成 T0 配置，下面说明的是后续 `tooling/tool_manager.py` 等代码落地后的职责和调用关系，不是已经上线的状态。

#### 它解决什么问题

工具管理器不是“工具函数集合”，而是所有工具调用的统一执行入口。它把容易出错的通用逻辑收在一层：

- 模型给的参数是否合法；
- 相同参数是否可以直接用缓存；
- 依赖连续失败时是否要暂停调用；
- 单次调用等多久、失败后要不要重试；
- 失败时是否返回降级数据；
- 结果是否需要重排；
- 每次调用的耗时、成功率、熔断状态记在哪里。

业务工具只关心“拿到合法参数后做什么”，不重复写超时、缓存、熔断和统计。

#### 核心对象

```text
ToolSpec      工具定义：名称、描述、JSON Schema、handler、超时/重试/缓存策略
ToolContext   单次请求上下文：user_id、session_id、request_id、intent、entities
ToolResult    统一返回：success、usable、degraded、cached、error_code、latency_ms
RegisteredTool  ToolSpec + ToolStats + CircuitBreaker，运行时状态与不可变定义分开
ToolManager   注册表 + 执行策略 + 统计
```

`ToolSpec.handler` 支持同步/异步函数，但永远不会直接暴露给模型。模型只看到 `ToolManager.definitions()` 返回的 `{name, description, input_schema}`。

#### 一次工具调用怎么走

```text
FunctionCallingLoop 收到 tool_use
  -> manager.execute(name, params, context, deadline)
       -> 查注册表：不存在 -> tool_not_found
       -> JSON Schema 校验：不合法 -> invalid_arguments
       -> 查缓存：命中且未过期 -> 直接返回 cached=True
       -> 熔断检查：OPEN 且未到恢复时间 -> 缓存/fallback/tool_circuit_open
       -> 执行 handler（单次超时 + 工具阶段 deadline）
       -> 失败且允许重试 -> 指数退避后重试
       -> 仍失败 -> fallback / ToolResult(usable=False)
       -> 成功且工具支持重排 -> Reranker 重排；失败保留原序
       -> 写缓存（检查版本，旧在途结果不回填）
       -> 更新统计
  -> 返回 ToolResult
FunctionCallingLoop 把 ToolResult 转成 tool_result 交回模型
```

几个关键约定：

- **参数错误不重试、不计熔断**：这是模型/调用方错误，不是依赖故障。
- **只读工具才自动重试**：`retry_safe=False` 的副作用工具不自动重试，避免重复退款/重复建单。
- **降级不是成功**：fallback 成功时 `usable=True, degraded=True`，模型需要说明“数据可能不完整”。
- **每个逻辑调用只记一次熔断结果**：重试多次仍失败只算一次失败，避免重试放大熔断。
- **缓存按用户隔离**：默认 `cache_scope=("user_id",)`，订单类结果不能跨用户复用。
- **缓存不挡恢复探测**：熔断到达恢复时间时，即使有缓存也要放一个半开探测，否则永远恢复不了。

##### 每次请求

管理器是进程级单例，**不会每个请求新建**。每个请求只创建 `ToolContext`：

```python
context = ToolContext(
    user_id=req.user_id,
    session_id=session_id,
    request_id=request_id,
    intent=intent_result.intent.value if intent_result else None,
    entities=intent_result.entities if intent_result else {},
)
```

请求级状态（用了哪些工具、每次调用的 trace、repair 次数、已执行过的参数）放在 `FunctionCallingLoop` 的本次调用局部变量里，不挂到共享的 `ToolManager` 上，避免用户 A/B 串数据。

## 第二件事：T1 工具契约与注册表

T1 只做工具层的稳定契约和注册表，不接参数校验、超时、缓存、熔断执行和 function calling，也不改 `/chat/stream`。目标是把 T2–T9 都要围绕的数据结构先固定下来，让 `ToolManager` 能脱离 FastAPI 和 LLM 独立实例化、独立测试。

### 1. 新增文件与职责

- `tooling/errors.py`：工具层错误契约。`ToolErrorCode` 收敛 `tool_not_found`、`invalid_arguments`、`tool_timeout`、`tool_circuit_open`、`too_many_tool_calls` 等稳定错误码，后续直接写进 `tool_result.error.code`；`ToolError` 是工具层异常基类，按错误码决定 `retryable`；`ToolValidationError` 预留给 T2，带 `path` / `validator`，用于生成模型可读的参数修复提示。
- `tooling/tool_manager.py`：契约与注册表。
  - `ToolContext`：单次请求上下文，字段为 `user_id / session_id / request_id / intent / entities`；构造时去掉首尾空白，并深拷贝 `entities`，调用方之后修改原字典不会影响已建上下文。
  - `ToolSpec`：frozen dataclass，包含 `name / description / input_schema / handler`，以及 `timeout_s / max_retries / retry_backoff_s / cache_ttl_s / cache_scope / retry_safe / supports_rerank / rerank_query_field / fallback`。`handler` 支持同步/异步函数，但永远不会出现在模型可见定义里。
  - `ToolResult`：统一返回 `success / usable / degraded / cached / reranked / truncated / attempts / latency_ms / error_code / error / retryable`。
  - `ToolStats` 与 `RegisteredTool`：把运行时可变的统计、熔断状态和不可变 `ToolSpec` 分开，避免冻结定义被运行期改写。
  - `CircuitState` / `CircuitBreaker`：三态状态机、`generation` 隔离、半开只放一个探测；使用注入的 `clock()`，测试不用真的等待恢复时间。
  - `ToolManager`：`register()` / `unregister()` / `get_spec()` / `names()` / `definitions()` / `execute()` / `get_stats()` / `fork()`。
- `tests/test_tool_manager.py`：59 项测试，覆盖契约校验、上下文复制、注册/注销/重名、定义输出、未知工具、同步/异步 handler、取消传播、统计、熔断状态机与 `fork()` 隔离。

### 3. 行为说明

**ToolSpec 校验：** 工具名必须是 1–64 位、小写字母开头、仅含小写字母/数字/下划线；`description` 不能为空；`handler`、`fallback` 必须可调用。`input_schema` 必须是 `type=object` 且包含 `properties`，缺省时自动补 `required: []` 和 `additionalProperties: false`；显式声明 `additionalProperties: true`、`required` 指向未声明字段、非对象 schema 都直接报错。schema 在构造时深拷贝，调用方之后再改原字典不会污染工具定义。

**注册表：** `register()` 遇到重名直接 `ValueError`，避免进程启动时静默覆盖；`unregister()` 返回是否真的删除了工具，并一起丢掉该工具的统计和熔断状态。注册表不依赖 FastAPI、LLM 或具体业务工具。

**模型可见定义：** `definitions()` 按工具名排序，只返回 `{name, description, input_schema}`，不包含 handler；每次返回的 schema 都是深拷贝，外部改动不会影响注册表。

**基础执行：** `execute()` 先查注册表，未知工具返回 `ToolResult(success=False, usable=False, error_code="tool_not_found")`，不抛异常、不创建统计。同步 handler 通过 `asyncio.to_thread()` 执行，异步 handler 直接 `await`；同步函数返回 awaitable 时也会补一次 `await`。handler 异常转成 `tool_handler_error`，`retryable` 跟随 `retry_safe`；`asyncio.CancelledError` 原样抛出，不记失败、不写缓存。

**统计：** `stats.total` 是逻辑调用数，`stats.attempts` 是物理尝试数（T3 接入重试后两者会分开）；成功/失败、连续失败、总延迟分别累计，`success_rate` 和 `avg_latency_ms` 由 `ToolStats` 计算。`get_stats()` 只返回计数、延迟和熔断状态，不返回参数或工具结果。

**熔断状态机：** 连续失败达到阈值后 `CLOSED → OPEN`；到达恢复时间后 `OPEN → HALF_OPEN`，只放一个探测，其余请求被拒绝；探测成功回到 `CLOSED`，失败重新 `OPEN`。状态变化时 `generation` 递增，旧代请求的迟到结果不能关闭新一轮熔断。T1 只提供状态机，`execute()` 还没有调用 `allow()` / `record_success()` / `record_failure()`，这部分在 T5 接入。

**fork：** 复制注册表条目，复用不可变 `ToolSpec`，但为每个工具新建 `ToolStats` 和 `CircuitBreaker`，并复制熔断阈值与恢复时间；在 fork 中注册工具、累计统计或触发熔断都不会影响原管理器。评测和测试可以拿它做隔离。

- 没有重排钩子（T6）、电商工具（T8）、Function Calling 循环（T9）和 `/chat/stream` 接入（T11）。
- `cache_scope` 目前只接受 `user_id / session_id / request_id / intent`；以后增加上下文字段时需要同步扩展白名单。

## 第三件事：T2 JSON Schema 参数校验

T2 把模型给的参数挡在 handler 之前：先校验、再执行；参数错误返回结构化 `ToolValidationError`，不重试、不计熔断、不进入缓存（缓存 T4 才实现）。同时提供 `schema_hint()`，让 T9/T10 能把“错在哪、该怎么改”交回模型。

### 1. 新增文件与职责

- `tests/test_tool_validation.py`：31 项测试，覆盖参数结构、去空白、缺必填、类型错、多余字段、枚举、数值范围、字符串长度/pattern、嵌套数组/对象路径、handler 不被调用、统计只增 `invalid`、连续参数错误不打开熔断，以及 `schema_hint()` 的结构与预算。
- `tooling/tool_manager.py` 中的 `validate_params(spec, params)`：模块级校验入口。只接受 JSON 对象，递归去掉字符串首尾空白，不做隐式类型强转；失败统一抛 `ToolValidationError`。
- `tooling/tool_manager.py` 中的 `_to_validation_error()`：把 `jsonschema.ValidationError` 转成中文短消息，保留 `path` 和 `validator`，供模型修复参数。
- `tooling/tool_manager.py` 中的 `_build_schema_hint()`：生成模型可读的精简 schema（required、字段 type/enum/min/max/length/pattern），不包含长 description。

### 2. 修改文件

- `tooling/tool_manager.py`：引入 `jsonschema`；`ToolSpec` 构造时用 `validator_for(...).check_schema()` 检查 schema 本身合法；`execute()` 在 handler 之前调用 `validate_params()`，参数错误只累加 `stats.invalid`；`ToolManager` 构造函数增加 `max_schema_hint_chars`（默认 800）；新增 `schema_hint()`；`fork()` 复制该预算配置。
- `tooling/__init__.py`：导出 `validate_params`，测试和后续 T9/T10 可以直接复用。
- `tests/test_tool_manager.py`：把“失败后成功”用例的 schema 补上 `ok` 字段。T2 启用 `additionalProperties: false` 后，未声明字段会被拒绝，旧用例不能再靠宽松 schema 通过。

### 3. 行为说明

**参数入口：** `params` 必须是映射，`None / list / str / 数字` 都返回 `invalid_arguments`；通过后转成普通 `dict`，递归 strip 字符串值（包括嵌套数组/对象里的字符串），不把 `"3"` 转成 `3`。

**校验规则：** 使用 `jsonschema.validators.validator_for(spec.input_schema)`，尊重 schema 自己的 `$schema`；T1 已在 schema 规范化时补上 `additionalProperties: false`，因此模型多传字段会被拒绝。校验在缓存、熔断和 handler 之前完成。

**错误结构：** `ToolValidationError` 固定 `code=invalid_arguments`、`retryable=False`，并带 `path` 与 `validator`。消息覆盖：缺少必填字段、不支持字段、类型不符、枚举越界、minimum/maximum、minLength/maxLength、pattern；嵌套错误路径形如 `items.1.sku`，不是只给顶层字段。

**执行与统计：** 未知工具仍然先返回 `tool_not_found`；校验失败返回 `ToolResult(success=False, usable=False, error_code="invalid_arguments", attempts=0)`，handler 一次都不会被调用。`stats.invalid` 单独累加，`total / attempts / failed / consecutive_fails` 不变，所以连续参数错误不会把熔断器推到 `OPEN`。

**schema 构造：** `ToolSpec` 在构造时额外执行 `check_schema()`，非法 schema（例如 `type: nonsense`）直接 `ValueError`，不会等到运行期才发现。

**schema_hint：** 默认预算 800 字符，按紧凑 JSON 计算。超预算时依次降级：完整约束 → 去掉 pattern 和数值/长度范围 → 只保留字段名；仍超长时逐字段截断并标记 `truncated: true`，同时把 `required` 过滤为实际保留的字段。未知工具返回 `None`。

### 4. 完整链路示例：一次 lookup_order 调用（按时间顺序）

下面用 `lookup_order` 走一遍从“注册工具”到“模型拿到最终回答”的完整顺序。每一步都标注当前状态：**已实现** 是现在代码里能跑的部分，**目标态** 是 T7–T11 才会接上的部分。

#### 4.1 注册工具：handler 和 schema 一起进入注册表（已实现，T1）

```python
spec = ToolSpec(
    name="lookup_order",
    description="按订单号查询订单状态、金额和支付状态；只读，数据为演示数据，不代表真实业务系统。",
    input_schema={
        "type": "object",
        "properties": {
            "order_id": {
                "type": "string",
                "minLength": 8,
                "maxLength": 20,
                "pattern": "^[A-Za-z0-9-]+$",
            }
        },
        "required": ["order_id"],
        "additionalProperties": False,
    },
    handler=lookup_order_handler,
)
manager.register(spec)
```

`handler` 支持同步/异步函数，但只存在于进程内注册表；模型永远看不到它。

#### 4.2 模型看到的 tools：`definitions()` 的实际输出（已实现，T1）

```json
[
  {
    "name": "lookup_order",
    "description": "按订单号查询订单状态、金额和支付状态；只读，数据为演示数据，不代表真实业务系统。",
    "input_schema": {
      "type": "object",
      "properties": {
        "order_id": {
          "type": "string",
          "minLength": 8,
          "maxLength": 20,
          "pattern": "^[A-Za-z0-9-]+$"
        }
      },
      "required": ["order_id"],
      "additionalProperties": false
    }
  }
]
```

只有 `name`、`description`、`input_schema` 三项。`definitions()` 每次返回 schema 深拷贝，外部改坏不会污染注册表；schema 在 `ToolSpec` 构造时已经过合法性检查并补上 `required` / `additionalProperties` 默认值。

#### 4.3 请求模型：带 `tools` 和 `tool_choice`（目标态，T7 + T9）

用户消息：`帮我查一下订单 A1001-001 现在到哪了？`

目标实现中，`FunctionCallingLoop` 会把 `manager.definitions()` 原样放进 Anthropic 原生 `tools` 参数，而不是把 JSON 拼进 prompt：

```python
turn = await llm.create_message(
    messages=[{"role": "user", "content": "帮我查一下订单 A1001-001 现在到哪了？"}],
    system=system_with_tool_policy,
    tools=manager.definitions(),
    tool_choice={"type": "auto"},
)
```

`core/llm.py` 的 `create_message(tools=...)` 属于 T7，`tooling/function_calling.py` 属于 T9；当前都还没有落地，所以这一步现在不会发生。

#### 4.4 模型返回：一个 `tool_use` 块（上游行为）

```json
{
  "role": "assistant",
  "content": [
    {"type": "text", "text": "我来查一下这个订单。"},
    {
      "type": "tool_use",
      "id": "toolu_01ABC123",
      "name": "lookup_order",
      "input": {"order_id": "A1001-001"}
    }
  ],
  "stop_reason": "tool_use"
}
```

模型只负责给出工具名和参数，不负责执行；`input` 是模型生成的不可信数据。

#### 4.5 编排层解析 `tool_use`（目标态，T7 + T9）

T7 把 content block 解析成 `ToolUse(id, name, input)`：

- `input` 已经是 dict 就直接用；
- 如果是 JSON 字符串，只尝试 `json.loads` 一次；
- 缺 `id` / `name`、`input` 不是对象、`id` 重复，记为协议错误，不执行任何工具；
- 解析成功后，T9 才调用 `manager.execute(name, input, context)`。

当前没有 `FunctionCallingLoop`，也没有 `ToolUse`，所以这一步同样不会发生。

#### 4.6 handler 之前：`execute()` 的实际校验过程（已实现，T1 + T2）

编排层最终只做一次调用：

```python
result = await manager.execute(
    "lookup_order",
    {"order_id": " A1001-001 "},
    context,
)
```

`execute()` 内部按以下顺序执行：

1. **查注册表。** 找不到 `lookup_order` 就返回 `tool_not_found`，不创建统计，也不抛异常。
2. **确认参数是对象。** `params` 必须是映射；`None`、`[]`、`"{}"` 都会变成 `invalid_arguments`。
3. **规范化但不强转。** `{"order_id": " A1001-001 "}` 去掉首尾空白变成 `{"order_id": "A1001-001"}`；字符串 `"3"` 不会被转成整数 `3`。
4. **JSON Schema 校验。** 用 `validator_for(spec.input_schema)` 检查必填、类型、`minLength`、`pattern` 和 `additionalProperties`；任何一项不通过，都在 handler 之前终止。
5. **校验通过后才计数并调用 handler。** `stats.total` / `stats.attempts` 加 1，同步 handler 放进 `asyncio.to_thread()`，异步 handler 直接 `await`。
6. **包装结果。** 成功返回：

```python
ToolResult(
    tool_name="lookup_order",
    success=True,
    usable=True,
    data={
        "order_id": "A1001-001",
        "status": "shipped",
        "amount": 199.0,
        "source": "demo",
        "authoritative": False,
    },
    attempts=1,
    latency_ms=1.7,  # 实际值随机器变化
)
```

#### 4.7 校验失败时发生什么（已实现，T2）

模型给错参数时，handler 一次都不会被调用。下面是当前代码的真实输出：

| 模型给的 `input` | `path` | `validator` | `error` |
| --- | --- | --- | --- |
| `{}` | `order_id` | `required` | 缺少必填字段: order_id |
| `{"order_id": 1001}` | `order_id` | `type` | 字段 order_id 类型应为 string |
| `{"order_id": "A1001-001", "user_id": "u1"}` | `user_id` | `additionalProperties` | 不支持字段: user_id |
| `{"order_id": "A1"}` | `order_id` | `minLength` | 字段 order_id 长度至少 8 个字符 |
| `{"order_id": "订单123456"}` | `order_id` | `pattern` | 字段 order_id 格式不匹配 |

以缺必填为例，`execute()` 返回：

```python
ToolResult(
    tool_name="lookup_order",
    success=False,
    usable=False,
    attempts=0,
    latency_ms=0.0,
    error_code="invalid_arguments",
    error="缺少必填字段: order_id",
    retryable=False,
)
```

统计只增加 `invalid`：

```text
total=0  attempts=0  success=0  failed=0  invalid=1  consecutive_fails=0  circuit_state=closed
```

也就是说：参数错误不重试、不执行、不计失败、不影响熔断。`path` 和 `validator` 目前保留在 `ToolValidationError` 上；`execute()` 对外只压成 `error_code` + `error`，把结构化的 `path` / `validator` / `schema_hint` 放进 `tool_result` 是 T9/T10 的工作。

#### 4.8 把 `ToolResult` 变成 `tool_result`（目标态，T9 + T10）

成功时，编排层为每个 `tool_use_id` 生成一条结果，`content` 是 JSON 字符串：

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01ABC123",
  "content": "{\"ok\": true, \"tool\": \"lookup_order\", \"data\": {...}, \"cached\": false, \"degraded\": false, \"truncated\": false}",
  "is_error": false
}
```

失败时把错误码、消息和 `schema_hint()` 一起回给模型，模型可以据此修参数或换工具：

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01ABC123",
  "content": "{\"ok\": false, \"tool\": \"lookup_order\", \"error\": {\"code\": \"invalid_arguments\", \"message\": \"缺少必填字段: order_id\", \"retryable\": false}, \"hint\": {\"type\": \"object\", \"required\": [\"order_id\"], \"additionalProperties\": false, \"properties\": {\"order_id\": {\"type\": \"string\", \"minLength\": 8, \"maxLength\": 20, \"pattern\": \"^[A-Za-z0-9-]+$\"}}}}",
  "is_error": true
}
```

#### 4.9 第二轮模型与最终回答（目标态，T9 + T11）

请求消息追加 assistant 的原始 content（保留 `tool_use` 块）和一条 user 的 `tool_result`，再请求模型。模型不再调用工具时，直接把文本按 SSE `delta` 发给前端：

```text
event: delta
data: {"text": "您的订单 A1001-001 已发货，..."}

event: done
data: {"status": "success", "tools_used": ["lookup_order"], ...}
```

这一轮不重新执行工具，也不把 `tool_use` / `tool_result` 写进对话历史，只有最终回答落库。当前 `/chat/stream` 还没有接入，仍走原来的 `llm.stream_chat`。

## 第四件事：T3 超时与重试

假设工具管理器收到一次“查订单 A1001 的物流”调用。这个只读工具每次最多等 3 秒，失败后最多自动重试 1 次。

1. **第一次查询（T3 加上单次超时）。** 物流接口等了 3 秒还没返回，工具管理器就结束这次等待，记一次超时。
2. **再查一次（T3 加上自动重试）。** 因为这是只读查询，工具管理器等约 0.1 秒，再用同一个订单号查一次。重试前会看工具阶段还剩多少时间。如果只剩 1 秒，第二次最多等 1 秒。预算用完就停止。
3. **返回结果（T3 补上尝试统计）。** 假设第二次很快返回“已发货”，这次工具调用就成功。统计上是 1 次工具调用、2 次尝试、1 次超时、1 次重试。若第二次也超时，就返回超时失败，因为重试次数已经用完。

T3 还让标记为 `retry_safe=False` 的工具在一次 `execute()` 内最多尝试一次。同一轮或跨消息再次调用属于独立的去重和幂等问题，当前尚未实现。

T3 原有验证结果为专项 28 项通过，全量 547 项通过、2 项跳过。
