### 1. 数据放在哪里，各层分别存什么

- `docker-compose.yml` 新增 `postgres:16-alpine` 服务，容器名 `commercemind-postgres`，宿主机入口 `127.0.0.1:5432`；应用容器通过 `postgres:5432` 连接。应用启动依赖 PostgreSQL healthy。
- 默认数据库名、数据库用户名均为 `commercemind`，可用 `POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD` 覆盖。应用用 `DATABASE_URL` 连接，示例在 `.env.example`，不要把生产密码写进代码。
- 表位于 `commercemind` 数据库的 `public` schema。数据文件挂载到容器内 `/var/lib/postgresql/data`，使用 Compose 命名卷 `postgres_data`，本项目实际卷名为 `commercemind_postgres_data`。Docker Desktop 的卷位于其 Linux 虚拟机中，不是仓库目录里的文件。
- PostgreSQL 保存 session 列表和完整的已完成消息，也承担持久化幂等结果。Redis 保存模型工作记忆、state、summary、锁和原有短期回执；摘要/压缩不会删掉 PostgreSQL 的完整历史。Chroma/长期记忆仍沿用既有模块，本次没有新增其表或检索流程。
- 浏览器 localStorage 继续保存用户/session 设置及本地消息缓存；侧栏与已完成消息恢复以后端查询为准，不再单靠 localStorage。数据库接入前只存在浏览器里的旧记录不会自动上传。

### 2. 库表设计

`public.sessions`：每个 session 一行，供侧栏列表使用。

| 字段 | PostgreSQL 类型 | 当前用途 |
| --- | --- | --- |
| `session_id` | `TEXT PRIMARY KEY` | 会话 ID；创建接口默认生成 UUID hex，聊天提交也兼容不存在的 session |
| `user_id` | `TEXT NOT NULL` | 所属用户；列表、删除和归属检查按它筛选 |
| `title` | `TEXT NOT NULL DEFAULT ''` | 空会话标题为空；首次成功提交时取问题前 80 字符，后续保持原标题 |
| `created_at` | `TIMESTAMPTZ` | 创建时间，默认 `now()` |
| `updated_at` | `TIMESTAMPTZ` | 创建或成功提交新 turn 的时间，读取不会更新 |
| `message_count` | `BIGINT DEFAULT 0` | 已完成消息数，每个成功问答加 2，不是 turn 数 |

列表索引为 `(user_id, updated_at DESC, session_id DESC)`，按最近活动排序，同时间时用 session ID 保持稳定次序。

`public.session_messages`：每条 user/assistant 消息一行；一个完整 turn 对应两行。

| 字段 | PostgreSQL 类型 | 当前用途 |
| --- | --- | --- |
| `message_id` | `BIGSERIAL PRIMARY KEY` | 服务端消息序号，也是向前翻页游标；序列不保证连续 |
| `session_id` | `TEXT` 外键 | 引用 `sessions.session_id`，删除 session 时 `ON DELETE CASCADE` |
| `user_id` | `TEXT NOT NULL` | 消息所属用户，查询和幂等检查使用 |
| `client_request_id` | `TEXT`，允许 NULL | 同一逻辑问答的幂等 ID，user 和 assistant 两行共用 |
| `role` | `TEXT` + CHECK | 当前只允许 `user` / `assistant`，没有 tool 消息行 |
| `content` | `TEXT NOT NULL` | 完整原始问题或完整回答 |
| `status` | `TEXT DEFAULT 'completed'` | 本次仅提交已完成消息，不持久化 pending/半截输出 |
| `created_at` | `TIMESTAMPTZ` | 事务写入时间；同 turn 两行可具有相同时间 |
| `metadata` | `JSONB DEFAULT '{}'` | user 默认空对象；assistant 保存执行 `request_id` 及本轮待提交 `state` 快照 |

消息分页索引为 `(user_id, session_id, message_id DESC)`。另有部分唯一索引 `(user_id, session_id, client_request_id, role) WHERE client_request_id IS NOT NULL`，阻止同一 session 的相同请求重复写入同角色消息。

**没有独立的 turns 表或 receipts 表。** 当前回执由相同用户、session、client_request_id 下的 user/assistant 两行组成：user 行用于校验原文，assistant 行提供完整回答及 `metadata.request_id`。两行同事务写入，所以成功结果与消息历史一起持久化。

### 3. Python 怎么连接、读写 PostgreSQL

`requirements.txt` 增加 `asyncpg`。`api/sessions.py` 的 `SessionRepository` 使用异步连接池，池大小 1–10；SQL 用 `$1`、`$2` 等参数占位，不拼接用户输入。

应用 lifespan 在启动时读取 `DATABASE_URL`，调用 `SessionRepository.connect()` 建池，并执行 `CREATE TABLE/INDEX IF NOT EXISTS`，将仓储挂到 `app.state.sessions`；退出时关闭连接池。当前是启动建表，不是独立迁移系统；没有配置 URL 时，session CRUD 返回 503，聊天仍保留原有无 PostgreSQL 的分支。

精简的实际调用方式如下（命名参数对应当前仓储方法，不是 ORM）：

```python
import asyncio
import os
from api.sessions import SessionRepository

async def main():
    repo = await SessionRepository.connect(os.environ['DATABASE_URL'])
    try:
        session = await repo.create_session(user_id='u1')
        sid = session['session_id']

        result = await repo.commit_turn(
            user_id='u1', session_id=sid,
            client_request_id='message-001', request_id='execution-001',
            question='退款何时到账？', answer='请提供订单信息。',
            state={'intent': {'intent': 'refund'}},
        )
        receipt = await repo.get_receipt('u1', sid, 'message-001')
        sessions = await repo.list_sessions('u1', limit=30, before=None)
        messages = await repo.list_messages('u1', sid, limit=50, before=None)
        print(result, receipt, sessions, messages)
    finally:
        await repo.close()

asyncio.run(main())
```

仓储内部用 `async with pool.acquire() as conn` 借还连接，用 `fetch`/`fetchrow` 读取、`execute` 写入。`commit_turn()` 使用 `async with pool.acquire() as conn, conn.transaction()`：异常退出回滚，正常退出提交。

### 4. 每个接口如何设计

浏览器使用 `/api` 代理前缀，下表写的是 FastAPI 实际路由。

| 接口 | 请求参数/内容 | 正常响应与数据库行为 |
| --- | --- | --- |
| `POST /sessions` | Query：`user_id`，1–128 字符；当前没有 JSON body | 返回新 session 元数据；只 INSERT 一行 sessions，消息数为 0，不调用模型、不写消息 |
| `GET /sessions` | Query：`user_id`、`limit` 默认 30/最大 100、可选 `before` | 返回 `{items, next_cursor}`；只读指定用户 session，按更新时间和 ID 倒序 |
| `GET /sessions/{session_id}/messages` | Path：session_id；Query：user_id、limit 默认 50/最大 100、before 为可选正整数消息 ID | 先查 session 归属，再读取一页消息；返回 `{items, next_cursor}`，每页消息以旧到新排列，metadata 为 JSON 对象，包含原 client_request_id |
| `DELETE /sessions/{session_id}` | Path：session_id；Query：user_id | 按用户及 session 删除，级联删除该 session_messages；返回 `{deleted: true}`，不存在或不属于该 user_id 返回 404 |
| `POST /chat/stream` | JSON：message、user_id、session_id、client_request_id、可选 skill_ids，沿用 ChatRequest 校验 | SSE：meta/delta/done/error；先查回执，未命中才生成；完整生成后事务提交数据库，再更新 Redis，再发 done |

session CRUD 在数据库未配置时返回 503，参数不合法通常为 422。消息列表不存在/不属于所传用户时为 404。当前没有额外的 `GET /sessions/{id}`、改标题 PATCH 或单条消息创建 REST 接口；消息写入只由 SSE 聊天完成路径触发。

会话列表 `next_cursor` 为本页最后一行的 `updated_at ISO时间|session_id`，下一页沿用返回的字符串，不自行构造；非法时间游标返回 422。消息列表先取最新 N 条，再反转为旧到新；向前翻页的 `next_cursor` 是本页最早的 message_id，下一页只查更小的 ID。页大小恰好等于 limit 时可能再多查一次空页以确认结束。

### 5. 什么时候读库、什么时候写库

**页面初始化/刷新与用户切换：** `historyStore.loadSessions()` 调 GET /sessions，前端每页 100 条遍历列表；若持久化选中的 session 仍属于返回列表则保留，否则选最近一条。随后调 GET messages 恢复当前 session。切换 session 重取最近 50 条，点击“加载更早消息”向前翻页。此时全是读操作，不新增历史或刷新 session 时间。

**点击新建：** 先在已加载的当前用户列表中复用空 session：优先当前空 session，其次其他空 session；只有不存在时调用 POST /sessions 写一行。空会话同时要求后端 message_count=0、本地没有消息且无正在发送的请求；失败/中断会话不会误用。busy 标志避免快速连点重复创建。

**发送前：** 前端先插入本地 pending 用户气泡，POST /chat/stream；有 PostgreSQL 且带 client_request_id 时，后端调用 `find_receipt(user_id, client_request_id)` 读消息对，可恢复原 session。没有命中才继续原有 Redis 回执检查、上下文读取和 LLM 流式生成。生成期间 delta 只缓存在服务端内存和浏览器临时消息中，不逐 token INSERT PostgreSQL。

**生成完整后：** 当前顺序已由早期“先 done 后提交”改为：

```text
完整回答非空
  → SessionRepository.commit_turn() 开始 PostgreSQL 事务
      → session 不存在则插入
      → SELECT session FOR UPDATE，检查所属 user_id
      → 再查本 session 下相同 client_request_id 的 user 消息
          → 同正文已有结果：返回首份规范答案及 request_id，不重复写入
          → 不同正文：拒绝本次提交
          → 无结果：INSERT user 消息 + INSERT assistant 消息
      → 更新 session.updated_at、message_count += 2、首次标题
  → PostgreSQL 事务提交成功
  → memory.commit() 更新 Redis working memory/state/短期回执
  → 触发既有异步记忆维护（按条件压缩/更新 summary 等）
  → 发送 done（使用事务返回的规范答案）
  → 前端锁定消息，重新查询列表和历史以刷新标题、消息数及内容
```

PostgreSQL 完整 turn 和持久化幂等结果是同一事务；Redis 是另一个系统，**两者不是跨库原子事务**。PostgreSQL 写失败则发送 `session_commit_failed` SSE error，不发成功 done；Redis 更新失败只记日志，仍以 PostgreSQL 中的成功结果发送 done，不丢掉持久化答案。

**中断：** 前端 abort 连接并保留已输出片段作为本地展示。若后端在生成完成前收到并执行取消，不进入完整 turn 的写库路径；已通过 POST /sessions 建立的空 session 仍可存在。取消与提交并发发生时不能回滚已经提交的结果，后续以数据库回执为准。

**网络重试：** 原 ID/原正文先读 PostgreSQL 消息对，命中则发送 meta、完整 delta、done，不再生成和重复插入。原 ID/不同正文在流开始前查到回执时返回 409；前端修改正文用新 ID。事务里同 ID/同正文重复提交时返回首个成功答案，不累加 message_count。当前索引的唯一约束范围是同一 session；不是独立的全用户幂等键表。

**删除：** DELETE 提交后前端移除缓存和列表，当前 session 被删则切到剩余最近一条。当前只删除 PostgreSQL session 和消息；Redis 工作记忆/回执、summary、Chroma 长期记忆不在这个删除接口里清理，不能将它描述成“所有记忆全量删除”。
