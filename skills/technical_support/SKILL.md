# 技术支持处理规范

## 适用场景

用户反馈登录失败、接口报错、配置错误、部署异常、超时、连接失败、回调问题或性能问题时使用。

## 处理步骤

1. 先复述现象，确认问题发生时间、是否持续复现、影响范围。
2. 收集最小必要信息：错误信息、错误码、截图或日志片段、使用环境、最近变更。
3. 按低风险顺序排查：网络、权限、配置、版本、依赖、服务状态。
4. 每一步说明目的，以及“如果结果是 A，下一步怎么走”，不要一次列出大量命令。
5. 需要解释具体错误码时，读取 `references/error-codes.md`。
6. 需要组织排查回复时，读取 `templates/troubleshooting-reply.md`。
7. 出现生产大面积故障、支付链路异常、数据丢失、权限越权或安全事件时，建议升级人工或二线技术。

## 资源使用

- 常见错误码解释：`references/error-codes.md`
- 排查回复模板：`templates/troubleshooting-reply.md`

## 回复要求

- 没有日志和错误码时，不要直接断定根因。
- 用户提供日志时，引用关键字段分析，不要泛泛而谈。
- 非技术用户使用低门槛语言；技术用户可以给出更具体的请求和验证方式。
- 建议重试时说明退避策略，不要让用户无限重试。

## 禁止事项

- 禁止编造服务状态、日志内容或内部错误原因。
- 禁止索要完整 API Key、Token、密码、验证码或私钥。
- 禁止建议删除生产数据、重装系统、关闭安全校验等破坏性操作。
- 禁止把“清缓存、重启、重装”作为唯一答案。

## 升级条件

生产环境大面积不可用、支付异常、数据丢失或错乱、权限异常、疑似攻击、密钥泄露，或用户按步骤排查后仍无法定位并提供了足够复现信息时，建议转人工或二线技术。
